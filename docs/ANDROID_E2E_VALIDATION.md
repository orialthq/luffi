# Android 이미지→그래프→보드 검증 기록

2026-09-27에 Android API 35 에뮬레이터에서 `dev` 앱(`com.orialthq.ori_beauty.dev`)과 로컬 개발 서버를 연결해 확인했다. 갤러리 선택기를 거친 앱 조작과 서버 상태를 함께 확인한 수동 검증이다. 같은 날 Google Photos의 외부 공유 시트도 별도 디버그 빌드에서 확인했다. **실물 휴대폰 검증은 아직 하지 않았다.**

## 실행한 흐름

| --- | --- | --- |
| 1. 레시피 캡처 | [`variation_recipe_tofu_egg_as_needed.png`](../server/test/fixtures/variation_recipe_tofu_egg_as_needed.png)를 갤러리에서 `바로 정리`로 추가 | 실제 `/v1/analyze` 호출 뒤 `두부 달걀 볶음`이 `레시피 / 내용 충분`으로 표시됐다. 앱의 원본 화면과 분석 화면을 대조했다. |

| 7. 재고와 필요량 | 레시피의 인분 계산을 실행하고 `tofu` 재고를 **빈칸**으로 기록한 뒤 필요 재료를 계산 | 빈칸이 `0g`이 아니라 `재고 미확인`으로 남았다. 쇼핑 화면에는 `tofu · 필요한 양 300 g · 재고 미확인`이 읽기 전용으로 표시됐다. |
| 8. 쇼핑 계획 반영 | 연결 화면에서 `쇼핑 계획에 반영 검토`를 누르고 새 변경안을 따로 승인 | 쇼핑 보드의 상품 선택 작업이 새 레시피 필요량을 참조하게 됐다. 상품 선택·구매는 자동으로 완료되지 않았다. |

최종 로컬 서버 상태에는 `user_confirmation` 출처 2개(각 보드의 사용자 확인), `capture_analysis` 출처 2개, 활성 `ingestion.extracted_field` 24개, `recipe.has_requirement`·`recipe.requirement_value` 각 1개, `scenario.connection_*` 관계가 있었다. `shopping.purchase_for_choice`, `shopping.actual_paid_krw`는 없었다. 이 수치는 이 검증 입력에서 관찰한 값이며 일반적인 정확도 지표가 아니다.

이 실행에서 재고 결과에 긴 내부 재료 ID가 그대로 보이는 화면 문제를 발견했다. 이름으로 표시하도록 고친 앱을 재설치한 뒤 같은 보드에서 `tofu: 확인 필요`로 표시되는 것을 확인했다.

## 외부 앱 공유와 재시도 추가 검증

Google Photos에서 같은 합성 레시피 PNG를 선택해 Android 공유 시트의 `luffi DEV`로 보냈다. 최초 빌드에서는 공유 인텐트가 `image/jpeg`를 선언하는 반면 제공자의 MIME과 실제 파일 서명은 `image/png`여서 앱이 이미지를 거절했다. 앱이 실제 파일 서명과 크기로 형식을 검증하고, 지원하는 이미지 형식끼리의 MIME 표기 차이는 허용하도록 수정했다. 수정 빌드에서는 앱을 종료한 상태에서 공유해도 홈에 도착 안내가 나타났고, 콘텐츠 목록에 원본 썸네일을 가진 새 항목 1개가 생겼다. Android가 보관하던 임시 첨부 파일은 앱 저장 후 정리됐다.

이후 같은 날 서버와 인증 토큰을 연결한 새 디버그 빌드에서 **Google Photos 공유부터 검토 완료 자료의 서버 가져오기까지** 다시 실행했다. 앱에서 미리 `바로 정리`를 선택하고 Photos의 합성 이미지 [`variation_recipe_tofu_egg_as_needed.png`](../server/test/fixtures/variation_recipe_tofu_egg_as_needed.png)를 공유했다. 앱의 도착 안내가 분석 완료 안내로 바뀌었고, 결과 화면에 원본 이미지와 `두부 달걀 볶음 / 레시피 / 내용 충분`이 표시됐다. 서버에 저장된 실제 분석 결과는 `gpt-5.6-luna`, `recipe`, 두부 `300 g`, 달걀 `2 개`, 소금 `약간`(단위 없음), 조리 순서 3단계였다. 이는 그 이미지 한 장에 대한 관찰 결과이지 모델 정확도 통계는 아니다.

검토 완료 자료의 서버 가져오기가 실패하면 요청을 그대로 보존한다. 네트워크가 돌아왔을 때 앱 복귀 시 자동 재시도하고, 개발 도구의 `서버 자료 동기화 대기 N건`에서 수동으로도 재시도할 수 있게 했다. 단위 테스트에서는 첫 요청의 응답 손실을 가정해 대기 1건을 만든 뒤 같은 프로세스에서 연결을 복구했다. 재시도가 동일한 `importId`와 요청 내용을 사용해 `synced`로 바뀌고, 추가 재시도는 새 요청을 만들지 않는 것을 확인했다.

위 실제 Photos 공유에서도 분석 완료 후 **서버 프로세스를 중단한 상태로** `정리함에 저장`을 눌렀다. 앱 메뉴에 `서버 자료 동기화 대기 1건`이 나타났고, 서버 상태 파일은 아직 없었다. 같은 인증 설정으로 서버를 다시 시작한 다음 메뉴의 수동 재시도를 누르자 대기 표시가 없어졌다. 격리된 서버 상태에는 `importReceipts` 1개, `capture_analysis` 출처 1개, 출처 버전 1개, 근거 5개, `ingestion.extracted_field` 주장 17개가 생겼다. 출처에는 `com.google.android.apps.photos`와 분석 실행 ID가 남았다. 앱의 저장된 요청도 같은 가져오기 ID로 `synced` 상태였다. 앱을 강제 종료하고 다시 열어도 서버의 영수증·출처·버전은 각각 1개였다. 이는 앱↔서버 실제 연결 중단·복구 검증이다. 서버가 요청을 처리한 직후 응답만 유실되는 경우의 중복 방지는 별도 자동화 테스트로 검증한다.

가져오기 단계는 **검토된 추출값을 출처·근거와 함께 보존**한다. 이 실험만으로 두부·달걀을 확정된 공용 식재료 엔티티로 병합하거나 레시피 보드를 자동 생성했다고 해석하면 안 된다. 앞 절의 보드·쇼핑 연결 검증은 앱 내부 갤러리 경로로 가져온 자료를 바탕으로 사용자가 별도로 확인하고 실행한 흐름이다.

## 외부 공유 출처로 보드 만들기와 과거 자료 가져오기

같은 에뮬레이터에 이전 공유 캡처와 서버의 격리 상태 파일을 유지한 채, 새 개발 토큰으로 앱과 서버를 다시 실행했다. `공통 활동 보드` → `확인한 자료로 레시피 만들기`에서 앞 절의 Google Photos 공유 결과 `두부 달걀 볶음`을 선택했다. 앱은 공유 이미지에서 읽은 재료를 바로 확정하지 않고 레시피 이름, 기준·목표 2인분, `tofu 300 g`을 별도로 입력·확인하게 했다. 사용자가 계획을 승인하자 레시피 활동 1개에 작업 4개(인분 계산, 재고 확인, 필요 재료 확인, 요리 완료 기록)가 생겼다. 서버의 새 `user_confirmation` 출처에는 `importedSourceId`가 **원래 Photos 공유의 `capture_analysis` 출처 ID**로 남았고, 확인한 레시피와 요구 재료 관계가 생성됐다. 이 실행에서도 모델이 추출한 두부·달걀·소금 전체가 사용자 확인 없이 작업 재료로 복사되지는 않았다.

새 개발 빌드의 메뉴에는 서버 연결 없이 예전에 `정리함에 저장`한 Google Photos 레시피 1건이 `기존 자료 서버 가져오기 1건`으로 나타났다. 앱 시작 시 자동 전송은 없었다. 메뉴에서 원본 이미지 파일은 보내지 않는다는 설명을 확인하고 `가져오기`를 누르자 대기 없이 동기화됐고, 서버 `importReceipts`는 기존 1개에서 2개로 늘었다. 두 가져오기 출처 모두 `com.google.android.apps.photos`를 기록했다. 과거 자료 메뉴는 이후 사라졌고 이미 연결된 레시피 보드는 그대로 1개였다. **같은 합성 이미지를 두 번 공유한 별개 캡처**이므로 출처 2개는 의도된 결과이며 이미지 내용만으로 중복·동일성을 확정하지 않는다.

같은 쇼핑 합성 이미지 [`variation_shopping_tofu_ingredient.png`](../server/test/fixtures/variation_shopping_tofu_ingredient.png)도 Google Photos에서 공유했다. 처음에는 앱에 남아 있던 `절약해서 정리` 설정 때문에 대기 상태가 되었고, `바로 정리`를 다시 선택해 공유한 캡처는 실제 모델 응답에서 `부침용 두부 300g / 상품 / 내용 충분`으로 표시됐다. 사용자가 `정리함에 저장`한 뒤 서버 가져오기 영수증은 3개(레시피 2개, 쇼핑 1개)가 됐다. 새 쇼핑 출처는 `com.google.android.apps.photos`를 기록했고, 쇼핑 계획 영수증의 `importIds`가 그 출처의 가져오기 ID를 가리켰다. 사용자가 쇼핑 목적을 입력하고 계획을 승인해 작업 2개를 만들었다. 이어서 앞서 만든 레시피 활동을 `레시피에 필요한 쇼핑`으로 연결했다. 서버에는 `recipe_shopping` 연결 1개가 남았으며 구매 완료나 요리 완료는 기록하지 않았다.

이때 **격리된 이전 서버에만 존재했던 같은 이름의 상품 캡처도 앱의 선택 목록에 남아 있는 문제**가 드러났다. 그 항목을 선택하면 현재 서버는 `IMPORT_NOT_FOUND`를 반환했고 보드가 생성되지 않았다. 현재 서버에 가져온 캡처를 선택하면 정상적으로 보드와 연결이 만들어졌다. 아래 절에서 이 문제를 수정하고 같은 앱 데이터·서버 상태로 다시 확인했다.

## 보드 출처의 서버 재검증

앱의 `synced`는 과거의 전송 성공 기록이므로, 보드에 들어갈 때 현재 서버의 가져오기 영수증과 활성 출처·버전을 다시 조회하도록 했다. 서버는 인증된 사용자 소유의 가져오기 ID를 한 번에 최대 100개 확인하고 `active`와 출처 ID, `deleted`, `missing` 중 하나를 돌려준다. 앱은 로컬의 출처 ID까지 일치하는 `active` 항목만 레시피·맛집·패션·뷰티·여행·일상 꿀팁·쇼핑·건강 보드의 자료 선택지에 넣는다. 서버에 연결할 수 없으면 검증되지 않은 자료를 선택지에 넣지 않고 안내한다. 이 조회는 자료를 다시 가져오거나 로컬의 과거 기록을 지우지 않는다.

자동 테스트에서는 현재 사용자에게 활성인 영수증, 삭제된 출처, 존재하지 않는 영수증, 다른 사용자 소유의 영수증, 같은 가져오기 ID가 다른 출처를 가리키는 경우를 확인했다. 검증 조회만으로 영수증이 추가되지 않는 것도 확인했다. 실제 개발 서버에는 레시피 2건과 쇼핑 1건의 영수증이 있었고, 이전 서버의 상품 가져오기 ID는 없었다. 새 Android 빌드에서 기존 앱 데이터를 유지한 채 `공통 활동 보드` → `저장한 상품으로 시작`을 다시 열자 `부침용 두부 300g`은 **현재 서버의 1건만** 보였다. 선택지에는 `캡처 표시 2,400원 · Google Photos · 2026-09-27 20:16`처럼 가격의 성격, 캡처 출처와 시각도 표시됐다. 실제 API 조회에서도 현재 쇼핑 ID는 `active`, 임의의 누락 ID는 `missing`이었다.

이는 **새 보드에 자료를 선택하는 시점**의 검증이다. 다른 화면의 로컬 `synced` 표시까지 서버와 실시간으로 맞추지는 않는다. 실물 휴대폰 검증은 별도 과제다.

보드 화면을 오래 열어 둔 경우도 앱 화면 테스트로 보강했다. 레시피·맛집·패션·뷰티·여행·일상 꿀팁·쇼핑·운동의 생성 대화상자를 열기 직전에 현재 서버의 영수증을 다시 확인하고, 살아 있는 후보만 보여준다. 대화상자에서 확인하는 동안 자료가 삭제될 수 있으므로 제출 직전에 선택한 ID를 한 번 더 확인한다. 하나라도 유효하지 않으면 생성 요청을 저장하거나 전송하지 않고 다시 선택하도록 안내한다. 쇼핑 상품 2개 중 하나가 삭제된 경우와 조회 연결 자체가 실패한 경우를 각각 화면 테스트로 확인했다. **이 시간차 사례를 실제 Android에서 삭제와 대화상자 조작으로 연속 검증하지는 않았다.**

## 이미 만든 보드의 출처 삭제

검토한 캡처 삭제 API를 통한 자동 검증에서는 캡처를 가져와 레시피 보드를 승인하고 인분 계산 작업까지 실행한 뒤 원본 가져오기 ID를 삭제했다. 서버의 영수증 상태가 `active`에서 `deleted`로 바뀌었고, 해당 보드·작업 결과·실행 영수증은 조회 대상에서 제거됐다. 같은 삭제 명령을 다시 보내도 새 작업이 생기지 않았다. 캡처에 의존하지 않는 별도 보드는 그대로 조회됐다. 이 경로는 개인정보 삭제에 따른 파생 자료 제거이므로 완료 결과를 보존하는 일반 정정 경로와 다르다.

앱 화면 테스트에서는 열려 있던 보드를 새로고침할 때 서버가 `NOT_FOUND`를 반환하면 이전 제목·작업·실행 버튼이 사라지고 삭제 안내와 `목록으로 돌아가기`가 나타나는지 확인했다. 목록으로 돌아가면 서버 목록을 다시 읽어 삭제된 보드를 제외한다. 네트워크만 실패한 경우에는 이전 보드를 읽기용으로 보여주되 쓰기를 막는 기존 동작을 유지한다.

Android API 35 에뮬레이터에서도 앞 절의 서버 상태를 **복사한 격리 데이터**로 다시 실행했다. 앱에서 `Tofu_for_recipe 쇼핑` 보드의 상품 선택 작업을 연 상태에서 로컬 삭제 API로 해당 쇼핑 캡처의 가져오기 ID를 삭제했다. 서버에서 보드 조회가 HTTP 404로 바뀐 뒤 앱의 새로고침을 누르자 과거 상품·작업이 사라지고 삭제 안내와 목록 이동 버튼이 나타났다. 목록으로 돌아간 화면에는 `Tofu egg stir fry` 레시피 보드 1개만 남았다. 서버의 보드 목록도 1개였고 레시피↔쇼핑 연결은 0개였다. 원본 검증 상태 파일은 변경하지 않고 복사본만 삭제했다. **실물 휴대폰은 아직 확인하지 않았다.**

## 다시 실행할 때

1. Android 에뮬레이터를 켜고 개발 서버를 `LUFFI_KERNEL_TOKEN`, `LUFFI_KERNEL_OWNER_ID`, `LUFFI_KERNEL_STATE_PATH`를 지정해 실행한다. 모델 API 키는 로컬 키체인에서 읽는다. 테스트용 토큰과 상태 파일은 저장소 밖에 둔다.
2. 같은 토큰을 넣은 Flutter 디버그 빌드를 설치한다. 에뮬레이터의 앱 서버 주소는 `10.0.2.2:8787`이다. 서버와 앱의 토큰이 달라지면 가져오기는 동기화되지 않는다.
3. 위 PNG 두 장을 기기 사진 저장소에 넣고 앱 `콘텐츠` → 추가 → `바로 정리` → 갤러리에서 각 이미지를 선택한다. 분석 결과와 원본을 대조하고 각각 `정리함에 저장`을 누른다.
4. 개발 도구의 `공통 활동 보드`에서 `확인한 자료로 레시피 만들기`, `저장한 상품으로 시작`을 순서대로 진행한다. 계획 승인 전후의 작업 상태를 확인하고 쇼핑 보드에서 레시피를 연결한다.
5. 레시피에서 인분 계산→재고 빈칸 기록→필요량 계산을 실행하고 쇼핑 보드에서 준비 목록을 확인한다. 새 쇼핑 계획 변경안을 만들고 별도 승인한다.
6. 서버 상태에서 가져오기 2건, 두 보드, 연결 1건과 구매·조리 결과 관계 부재를 확인한다. 새 모델 응답은 기존 저장 응답과 다를 수 있으므로 화면의 제목·가격·근거를 매번 별도로 확인한다.
7. 외부 공유 경로는 앱에서 `바로 정리`를 고른 후 Google Photos에서 레시피 PNG를 공유 시트의 `luffi DEV`로 보낸다. 분석 완료 안내를 열어 원본과 재료·분량·순서를 대조한다.
8. 중단·복구를 반복 검증하려면 `정리함에 저장` 직전에 서버를 중지한다. 저장 후 대기 1건을 확인하고 동일한 토큰·상태 파일로 서버를 재시작해 메뉴에서 재시도한다. 대기 표시가 사라지고 그 공유의 가져오기 영수증·출처·버전이 각각 한 개씩인지 확인한다. 앱을 강제 종료하고 다시 열어도 서버 측 건수가 늘지 않는지 확인한다.
9. 이 출처로 보드를 확인하려면 `공통 활동 보드`에서 `확인한 자료로 레시피 만들기`를 열어 해당 공유 결과를 선택한다. 레시피 내용과 분량·재료를 직접 확인하고 계획을 승인한 다음, 확인 출처의 `importedSourceId`와 보드 작업 4개를 확인한다.
10. 과거 자료 검증은 토큰 없이 이미 저장한 별도 캡처를 남겨 둔 상태에서 새 개발 빌드를 설치한다. 메뉴의 `기존 자료 서버 가져오기 N건`에서 설명을 보고 명시적으로 확인한다. 자동 전송 여부, 출처 건수, 메뉴의 대상 건수 감소를 확인한다.

앱을 토큰 없이 실행해 `정리함에 저장`한 과거 캡처에는 `reviewedImport`가 생기지 않는다. 새 개발 빌드에서 대상 건수를 확인하고 명시적으로 가져올 수 있다. 저장된 분석·확인 기록이 없는 캡처와 데모는 대상이 아니며, 실패한 요청은 재시도 대기에 남는다. 서버가 교체·초기화된 뒤의 보드 자료 선택은 위의 서버 재검증을 거친다. 실물 휴대폰 검증은 아직 남아 있다.

공개 합성 이미지 21장의 원본 해시·녹화된 응답·근거 참조는 [`image_fixture_corpus.test.js`](../server/test/image_fixture_corpus.test.js)에서 반복 검사한다. 이것은 저장 응답 회귀 검증이며 새 모델의 정확도 검사는 아니다. 로컬 비공개 17개 평가 입력의 전체 매니페스트가 현재 작업 환경에 없어 그 평가 수치를 새로 산출하지 않았다.
