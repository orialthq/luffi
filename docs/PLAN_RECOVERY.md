# 변경된 근거의 계획 재검토

가져온 캡처의 일반 필드는 `GET /v1/kernel/ingestion/editable-fields/{importId}`로 현재 값·원래 분석값·원본 텍스트 근거·정정 버전을 읽는다. 앱의 저장한 정보 화면에서 원본 이미지를 보며 값을 정정할 수 있다. `POST /v1/kernel/ingestion/field-corrections`는 `{commandId,importId,path,value,expectedRevision,confirmed:true}`를 받는다. 서버는 소유자, 원본 자료, 분야별 허용 경로, 활성 근거, 필드 버전을 확인하고 사용자 확인 출처·버전·근거를 만든 뒤 같은 필드의 assertion을 원자적으로 정정한다. 원래 분석 스냅샷은 보존하고 현재 사용 값만 바꾼다. 같은 명령은 재전송해도 한 번만 적용되며, 오래된 버전이나 다른 값으로 재사용한 명령은 거절한다. 원본을 삭제하면 연결된 정정 출처와 명령 결과도 삭제된다.

현재 일반 필드 편집 범위는 맛집의 장소명·지역·주소, 여행의 장소명·지역, 패션·뷰티의 상품명, 생활 꿀팁과 건강 운동의 제목·단계 내용이다. 레시피의 재료 그래프와 쇼핑의 가격 확인은 각각 별도 검증 경로를 사용한다. 보드가 이미 만들어졌다면 정정 직후 변경 검토가 필요하며, 사용자가 수정안을 승인하거나 시작된 작업은 새 활동으로 이어가야 한다.

레시피는 보드의 **레시피 정정**에서 `GET /v1/kernel/recipe/editable/{activityId}`로 확인된 현재 레시피와 원래 확인 내용을 읽는다. 제목·기준 인분·재료의 이름/양/선택 여부/비례 방식·조리 단계의 내용과 순서를 함께 편집한다. `POST /v1/kernel/recipe/corrections`에는 `{commandId,activityId,expectedAssertionId,recipe:{title,baseServings,ingredients,steps},confirmed:true}`로 전체 대체안을 보낸다. 서버는 소유권, 확인 근거, 그래프의 활성 연결, 현재 assertion 버전, 재료·단계 ID의 유일성, 계획 생성 가능성을 먼저 검증한다. 변경이 없거나 오래된 버전은 거절한다. 성공하면 하나의 트랜잭션에서 레시피 본문과 각 재료 항목·재료 실체 연결·조리 단계 연결을 함께 정정하고, 삭제한 항목의 연결을 철회한다. 각 새 assertion에는 원래 확인 근거와 이번 사용자 확인 근거가 붙는다. 재료 이름을 다른 재료로 바꾸면 새 재료 ID를 사용하므로 이전 재고와 잘못 연결되지 않는다. 같은 명령 ID의 재전송은 중복 정정을 만들지 않는다. 원본 자료나 최초 확인 출처를 삭제하면 연결된 정정도 함께 철회된다.

서버는 활성 레시피 본문, 재료 항목·연결 수, 조리 단계·연결 수와 순서가 모두 맞을 때만 다시 계획한다. 정정 뒤에는 보드에서 영향받은 작업을 검토해 수정안을 승인한다. 이미 시작한 작업의 입력·결과는 보존하고, 필요한 경우 최신 레시피로 새 활동을 만든다. 조리 단계는 계획 제안과 요리 작업에도 순서대로 표시한다.

확인한 자료의 assertion을 정정하거나 철회하면 활동의 지식 그래프 구독이 변경을 감지한다. 기존 작업은 그 사이 실행할 수 없다. 보드는 `GET /v1/kernel/boards/{activityId}/review`로 변경 전후 값, 영향을 받는 작업, 수정 가능 여부를 읽는다. 원본이 삭제되어 활동 자체가 제거된 경우에는 보드를 찾을 수 없으며 과거 값을 다시 내보내지 않는다.

자동 수정안은 레시피·맛집·패션·뷰티·여행·생활 꿀팁·쇼핑·건강 운동 시나리오를 지원한다. 쇼핑은 사용자가 확인한 표시 가격을 다시 읽는다. 레시피는 활성 `recipe.confirmed_recipe`와 각 활성 `recipe.requirement_value`가 일치할 때만 재료 정보를 다시 읽는다. 서로 어긋나면 `RECIPE_GRAPH_CONFLICT`로 막는다. 나머지 분야는 캡처의 최신 활성 `ingestion.extracted_field`에서 제목·장소명·단계 내용을 다시 읽는다. 값이 철회됐거나 근거가 없거나 여러 활성 값이 충돌하면 `blocked`와 이유를 반환하며 과거 분석값으로 되돌아가지 않는다. 분야 분류처럼 계획 후보에 쓰이지 않는 자료의 변경, 자원·검색 결과의 변경, 지원하지 않는 활동은 별도 검토가 필요하다.

수정 가능하면 `POST /v1/kernel/planning/review-proposals`에 `{activityId,commandId,expectedRevision,confirmed:true}`를 보낸다. 서버는 새 Context에서 후보를 다시 만들고 현재 계획과 비교한다. 미승인 초안은 새 초안으로 교체한다. 승인된 계획은 아직 시작하지 않은 작업의 입력만 바꾸는 patch를 만든다. 작업 목록이나 의존·데이터 연결이 변경된 계획은 원래 시나리오의 구조로 덮어쓰지 않고 `REPLAN_UNAVAILABLE`로 막는다. 이미 시작한 작업의 입력·고정된 값·실행 결과·구매 보고는 수정하지 않으며 `STARTED_TASK_PROTECTED`를 반환한다. 사용자는 이 경우 과거 기록을 남겨 두고 새 활동에서 다시 확인해야 한다.

수정안 생성은 실행이 아니다. 보드는 변경 전후와 영향받는 작업을 보여주고, 사용자가 `POST /v1/kernel/planning/accept`로 승인해야 새 Context가 구독되고 변경 알림이 해소된다. 이전 제안은 `superseded` 처리된다. 수정안 명령 ID의 재전송은 같은 제안을 돌려주며, 원본 삭제 후 재전송은 거절한다. 새 근거가 제안 뒤 또 바뀌면 승인도 `CONTEXT_STALE`로 실패한다.

이미 시작한 작업 때문에 `STARTED_TASK_PROTECTED`가 반환되면 보드의 **새 활동으로 이어가기**를 사용할 수 있다. `POST /v1/kernel/planning/review-successors`에 `{activityId,commandId,expectedRevision,confirmed:true}`를 보내면 서버가 이전 활동의 시나리오 조건과 최신 근거를 다시 검증해 독립적인 새 활동과 미승인 계획을 만든다. 사용자가 새 계획을 승인하기 전까지 실행할 작업은 생기지 않는다. 이전 활동의 작업·결과는 수정하지 않고, 두 보드에서 이전/이후 활동을 열 수 있다. 새 활동 생성 API에 `continuationOf`를 직접 넣더라도 서버가 복원한 입력과 일치하지 않으면 연결을 거절한다. 같은 명령 재전송은 새 활동을 중복 생성하지 않으며, 원본 삭제는 그 원본에 의존하는 두 보드를 함께 제거한다.

회귀 테스트는 실제 분석 응답에서 이전·현재 가격을 구분해 정정한 쇼핑 보드, 재료 수량과 요구량 assertion을 함께 정정한 레시피 보드, 나머지 여섯 분야의 후보 필드 정정과 승인, 삭제된 원본의 보드·수정안 재사용 거부를 검증한다. 시작한 쇼핑·레시피·뷰티 작업에서 새 보드를 만들고 옛 결과를 보존하는 과정도 검증한다. 클라이언트 테스트는 변경 설명, 수정안 생성, 별도 승인, 새 활동 이동을 확인한다.
