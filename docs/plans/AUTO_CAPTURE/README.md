# 자동 수집

찍기만 하면 들어와서 정리되어 있는 것. 저장하려고 사용자가 하는 일이 없어야
한다.

## 목표

안드로이드에서는 이렇게 된다: 스크린샷을 찍으면 앱을 켜지 않아도 몇 초 안에
분석과 정리가 끝나 있다. 아이폰도 **최대한 그것에 가깝게** 만든다. 완전히
같아지지는 않는다 — 이유는 아래에 있다.

## 지금

| | 아이폰 | 안드로이드 |
|---|---|---|
| 들어오는 길 | 앱 열기 → `+` → 스크린샷 가져오기 → 사진 고르기. **7단계, 앱을 옮겨 다님** | 공유 시트 → Trun On. 2탭. 빠른 설정 타일도 있음 |
| 공유 확장 | **없음.** 타겟이 앱과 테스트 둘뿐 | 인텐트로 받음 |
| 정리 | 캡처마다 사용자가 눌러야 `organized` | 같음 |
| 분석 | **한 장씩 순서대로.** 10장이면 200초 | 같음 |
| 실패 | 공유함에서 찾아 직접 눌러 재시도 | 같음 |

핵심 코드: 인앱 피커 `ios/Runner/Share/CapturePickerPresenter.swift`, 검증·복사
`IncomingShareIngestor` (양쪽), Dart 인입 `MethodChannelIncomingShareService`,
직렬 분석 `app_controller.dart` `_drainIncomingSharesOnce` → `_analyzeCapture`.

## 바꿀 수 없는 한계

애플은 **"사진이 새로 생겼다"는 이유로 앱을 깨우는 API를 주지 않는다.**

- 사진첩 변화 감지(`PHPhotoLibraryChangeObserver`)는 앱이 메모리에 있을 때만
- 백그라운드 새로고침은 iOS가 자기 재량으로 하루 몇 번
- 단축어 자동화에 "스크린샷 찍었을 때" 트리거는 없다

그래서 아이폰에서 **"설정 없이 + 앱 안 켜고 + 즉시"** 세 가지를 동시에 갖는
방법은 없다. 어떤 앱도 못 한다. 둘까지는 된다.

| | 캡처만 인식 | 앱 안 켜고 | 즉시 |
|---|---|---|---|
| 안드로이드 | ✓ 폴더 기준 | ✓ | ✓ 수 초 |
| 아이폰 · 자동 수집 | ✓ 시스템 플래그 | ✓ | ✗ 다음 앱 실행 / 새로고침 때 |
| 아이폰 · 단축어 자동화 | ✓ | ✓ | ✓ 앱 나갈 때 — 자동화 한 번 만들어야 |
| 아이폰 · 공유 확장 | ✓ | ✓ | ✓ — 탭 3번 |

안드로이드는 OS가 "새 이미지가 생기면 이 작업을 깨워라"를 지원한다
(`JobScheduler` 콘텐츠 트리거). 그래서 아이폰의 우회가 전부 필요 없다.

## 가져오는 범위

사용자와의 약속이다. 양쪽 플랫폼 공통.

| 들어간다 | 안 들어간다 |
|---|---|
| 권한을 허용한 시각 이후에 찍은 시스템 스크린샷 | 그 전에 있던 스크린샷 — 설치 전 것, 다른 기기에서 동기화된 옛것 |
| | 카메라로 찍은 사진 — 조회 자체를 안 한다 |
| | 화면 녹화 — 영상이라 다른 유형 |
| | 사파리·인스타에서 "이미지 저장"한 것 — 스크린샷이 아니다 |

"마지막 확인 시각"의 첫 값이 **권한 허용 시각**이라 그 전은 영영 보이지
않는다. 권한 프롬프트는 "모든 사진"이지만 코드가 읽는 것은 이 범위뿐이고,
권한 문구에 그렇게 적으면 그것이 사실이 된다.

이전 스크린샷을 가져올지 한 번 묻는 선택은 나중에 붙일 수 있다. 기본은
"이후만".

## 세 겹 — 아이폰

1겹만으로 사용자는 권한 한 번 허용한 것 말고 한 일이 없다. 2겹은 원하는
사람만. 3겹은 1·2겹이 못 잡은 나머지의 기다림을 줄인다.

**1겹 · 항상 켜져 있는 것** — 셋은 서로 다른 슬롯이다.

| | 누가 깨우나 | 언제 | 시간 | 믿을 만한가 |
|---|---|---|---|---|
| 앱 열 때 | 사용자 | 켜거나 돌아올 때 | 제한 없음 | 항상. 바닥이다 |
| 백그라운드 새로고침 | iOS | iOS 재량, 하루 몇 번 | 30초쯤 | 되면 좋은 것. 설정에서 꺼놨거나 저전력이면 안 돈다 |
| 충전 중 처리 | iOS | 충전 중 + 유휴 | 몇 분 | 조건이 명확해 예측된다 |

"열었을 때 이미 끝나 있다"를 만드는 힘은 **충전 중 처리 > 새로고침** 순이다.
새로고침은 시점을 고를 수 없고 30초라 한두 장이 한계다. 충전 중 처리는 밤에
꽂아두면 낮에 쌓인 것을 다 끝낸다. 앱 열 때 수집은 둘 다 실패해도 받쳐준다.

**2겹 · 선택**
- 앱 인텐트 "새 스크린샷 정리" + 사용자가 만드는 자동화 "인스타그램을 닫으면
  실행". 그 앱을 나가는 순간 처리된다

**3겹 · 기다림 단축**
- 분석을 동시에 보낸다. 10장이 20초
- 업로드를 줄인다 — 얼마나 줄여도 되는지는 잰 뒤

다 합치면: 낮에 찍은 것은 새로고침이 일부, 밤 충전이 나머지를 처리한다. 낮에
바로 열어도 남은 것은 동시 처리로 수십 초. 자동화를 만든 사람은 앱 나갈 때
이미 끝나 있다.

자세한 것은 [IOS](IOS.md).

## 비용

자동 수집은 호출 수를 늘린다. 세 겹이 기다림을 줄이는 동안 요금은 이 셋으로
다룬다. 서로 독립이라 다 같이 갈 수 있다.

| 레버 | 절감 | 조건 | 확인된 것 |
|---|---|---|---|
| 병렬 처리 | **0%** | — | 호출 수가 같다. 빨라질 뿐 싸지지 않는다. 실측 4장 38초 → 10초 |
| 이미지 축소 | 토큰 비례 | 글자 인식이 유지되는 선을 재서 | 서버가 `detail: "original"`로 원본 해상도를 보낸다(`prompt.js:121`). 비율은 재기 전엔 모른다 |
| **배치 API** | **50%** | 24시간 안에만 받으면 되는 호출 | 공식 문서. `/v1/responses` 지원 — 지금 요청 모양 그대로 들어간다. **단, `gpt-5.6-luna`는 지금 배치에서 `model_not_found`가 난다**(개발자 커뮤니티 보고, 2026-09). 문서는 5.6 계열을 지원한다고 하니 구멍이거나 일시적인 것일 수 있다. 만들기 직전에 다시 확인하고, 그때도 안 되면 배치용으로 다른 5.6 변종을 쓸지 잰다 |

luna는 이미 5.6 중 가장 싼 모델이다(Sol 대비 80% 저렴). 배치 50%는 그 위에
얹히는 것이라 절대 금액은 Sol에서 배치를 쓰는 것보다 작다. 그래도 호출량이
커지면 의미가 있다.

배치는 밤 처리 슬롯과 짝이다. 즉시 원하는 것(공유로 넣은 것, 앱을 열어 보는
것)은 지금처럼 바로 보내고, 밤에 밀린 것만 배치로 보내면 그 몫이 반값이 된다.

**플래그가 아니라 구조다.** 배치는 서버에 큐가 생긴다는 뜻이다 — 받아서
모아두고, 제출하고, 24시간 안에 결과를 받아, 앱이 다음에 열 때 가져가게 한다.
지금 서버는 요청 하나에 응답 하나로 끝나는 모양이라, 상태를 들고 있는 층이
하나 더 생긴다. 앱도 바뀐다 — 지금은 보낸 요청의 답을 90초 기다릴 뿐,
"그 사이 끝난 것"을 나중에 물어보러 오는 경로가 없다. 밤 슬롯이 하는 일도
"분석"이 아니라 "제출"까지가 된다. 그래서 순서상 자동 수집이 돌아간 뒤,
호출량이 실제로 보인 다음에 한다.

## 전제 — 먼저 고칠 것

자동 수집은 캡처가 **사용자 손을 거치지 않고 대량으로** 들어오게 만든다.
저장 경로를 훑어 확인된 약점 세 개는 그 전에 막아야 한다. 지금은 한 장씩
사람이 넣으니 드러나지 않았을 뿐이다.

**1. 레코드 하나가 깨지면 서재 전체가 사라진다.**
`AppSnapshotCodec.decode`는 캡처 하나라도 형식이 어긋나면 던지고
(`app_snapshot_store.dart:331`), `_restoreSnapshot`은 그걸 `debugPrint`로 삼키며
(`app_controller.dart:1471`), 다음 `_persistState`가 빈 목록을 덮어쓴다
(`:1645`). 바로 옆 연상어 사전 디코더는 "잘못된 항목은 그 항목만 잃는다"고
짜여 있다(`:338-355`). 캡처에도 같은 관용을 준다 — 깨진 레코드는 건너뛰고
기록하고, 나머지는 산다.

**2. 분석이 직렬이다.** 드레인 루프가 한 장씩 `await`한다
(`app_controller.dart:672`). 동시에 보내되 상한을 둔다. 상한값은 서버와 폰에서
재서 정한다.

**3. 실패는 손으로만 되살아난다.** `AnalysisServiceException.retryable`은
만들어져 있고(`remote_content_analysis_service.dart:12`) 읽는 곳이 없다.
`analysis_timed_out`과 `image_too_large`가 똑같이 취급된다. 일시적 실패는
간격을 두고 자동 재시도하고 네트워크가 돌아오면 다시 붙인다. 영구 실패만
사용자에게 보인다.

부차적으로 확인된 것들 — 지금 급하지 않지만 자동 수집 뒤에 다시 본다:
`retryAnalysis`가 `review`·`groupId`를 버리고 그룹 참조를 끊는 것(`:1342`),
첨부 경로가 절대 경로라 iOS 재설치 때 전부 무효가 되는 것, iOS 스냅샷 16MB
상한이 "없음"과 구분되지 않는 것, 여러 장 공유가
`multiple_images_not_supported`로 실패하는 것.

## 순서

**0. 전제 셋** — 위. 3겹의 "동시 분석"이 여기 포함된다. 제일 작고, 나머지가
전부 이걸 전제로 한다.

**1. 아이폰 · 앱 열 때 수집** — 사진첩 권한 문구 추가, 스크린샷 플래그로
조회, 기존 `IncomingShareIngestor`로 넘기기. 이것만으로 7단계가 0단계가 된다.
→ [IOS](IOS.md)

**2. 안드로이드 · 스크린샷 직후 수집** — `JobScheduler` 콘텐츠 트리거.
안드로이드는 이 한 단계로 목표에 도달한다. → [ANDROID](ANDROID.md)

**3. 아이폰 · 백그라운드 슬롯** — 새로고침과 충전 중 처리. 1번 위에 얹는다.

**4. 아이폰 · 앱 인텐트 + 단축어** — 온보딩 안내 포함. 선택 사항이라 늦어도
된다.

**5. 업로드 축소** — 원본 대비 태그 재현성을 잰 뒤에만.

**6. 공유 확장** — 안드로이드와의 대칭. 앱 그룹으로 저장소를 옮겨야 해서
마지막.

1·2번이 끝나면 "실제 스크린샷 100장"이 노력 없이 쌓인다. 그것이
[태깅](../../TAGGING.md)의 뒷정리 단계와 "확신 높은 것 자동 정리"의 기준선을
만든다.

## 측정

- **열었을 때 이미 분석이 끝나 있는 비율** — 이 계획의 핵심 숫자. 1겹만일
  때, 3번을 얹었을 때, 자동화까지 있을 때 각각
- 앱을 열고 첫 태그가 붙기까지 초
- 백그라운드 새로고침이 실제로 도는 빈도 — iOS 재량이라 잰 값만 믿는다
- 잘못 들어온 스크린샷 비율 — 민감한 것, 저장할 뜻이 없던 것
- 축소한 이미지의 태그 재현성 — 원본과 같은 태그가 나오는가

## 아직 정하지 않은 것

**민감한 스크린샷.** 자동 수집이 되면 계좌 잔액, 메신저, 인증번호도 사용자
눈에 띄기 전에 서버로 간다. 세 길이 있다.

| | 편의 | 위험 |
|---|---|---|
| 다 보낸다 | 최대 | 민감한 것도 분석 서버로 |
| 기기에서 먼저 거른다 | 거름망 정확도만큼 | 기준을 지어낼 수 없다 — 데이터 필요 |
| 일단 다 보내고 규칙은 나중에 | 최대 | 지금은 본인 맥이 서버라 감당 가능. 배포 전엔 반드시 |

추천은 셋째. 지금 단계에서 제일 중요한 것은 실제 스크린샷이 쌓이는 것이고,
거름망은 그 데이터를 보고 만드는 게 맞다. **결정은 아직이다.**

**업로드 축소 비율** — 잰 뒤.

**확신 높은 것 자동 정리** — 이 계획 밖. 캡처마다 확인을 요구하는 것도
마찰이지만, "확신"의 선은 실제 저장물이 쌓여야 그을 수 있다.
