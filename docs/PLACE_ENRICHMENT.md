# 장소 보강 — 축 설계와 측정 기록

저장소: <https://github.com/orialthq/luffi>

맛집·카페 캡처에 `예약·대기` 축을 붙이는 파이프라인의 설계와, 그렇게 만든
근거가 된 측정치입니다. 여기 적힌 숫자는 모두 실제 호출로 재본 것이고, 다시
재려면 시간과 API 비용이 드니 결론과 함께 남깁니다.

## 파이프라인

```
[0] 스크린샷 → Luna 비전          상호명 · 지역 · 폴더
[1] 분기 (코드)                  맛집·카페 + 상호명 있음? 아니면 종료
[2] 수집 → Luna 웹검색            프로브 3개 병렬, 원문 문장만 발췌
[3] 식별 (코드)                  어느 가게인가. 애매하면 중단
[4] 판단 → Luna                  발췌만 근거로 라벨. 검색 없음
[5] 검증 (코드)                  quote가 발췌에 없으면 라벨 버림
```

핵심은 **[2]와 [4]를 분리한 것**입니다. 검색한 모델에게 라벨까지 맡기면 그
모델이 추론을 다 해버립니다. 수집은 "문장을 그대로 옮겨라, 해석 금지"로
계약을 걸고, 판단은 그 문장만 보게 합니다.

그 분리가 [5]를 가능하게 합니다 — 판단이 쓴 근거가 발췌에 없으면 지어낸
것입니다. 문자열 비교로 잡힙니다.

### [2] 프로브 3개

축마다 사실이 사는 곳이 다릅니다. 질의 하나로는 다 닿지 않습니다.

| 프로브 | 도메인 | 질의 |
| --- | --- | --- |
| listing | 다이닝코드 · 식신 · 당근 · 망고플레이트 | `{상호} {지역}` |
| booking | 캐치테이블 · 네이버예약 · 테이블링 | `+ 예약` |
| experience | 제한 없음 | `+ 웨이팅 대기 줄 오픈런 후기` |

병렬이라 가장 느린 하나만큼(8~13초)만 걸리면서 발췌가 3배가 됩니다
(10건 → 29건).

`booking` 프로브에 그 가게 페이지가 있으면 **코드가 `예약 가능`을 확정**합니다.
페이지 존재는 사실이고, 모델에게 물을 일이 아닙니다. 이미 `예약 필수`가
나왔다면 덮지 않습니다.

`experience` 프로브를 도메인 무제한으로 둔 이유: 지금까지 가장 유용한 편의시설
목록이 **당근**에서 나왔는데, 손으로 쓴 도메인 목록에는 없던 곳입니다.

### [3] 식별이 게이트인 이유

잘못된 가게의 정보를 붙이는 것이 정보가 없는 것보다 나쁩니다. 어니언 성수를
저장한 사람에게 어니언 미아의 영업시간을 확인된 사실로 보여주는 건 적극적인
오정보입니다. 그래서 **확정 못 하면 판단을 아예 실행하지 않습니다.**

실제로 겪은 것들:

- `방콕테이블` 검색에 `샐몬 무쌉`이 두 번 잡혔습니다 → 탈락
- `하동관` / `하동관 본점` / `하동관 명동본점` 은 한 가게입니다 → 병합해서 확정
- `화육계 - 을지로3가 닭발, 계란말이 맛집` (페이지 제목 통째) → 탈락
- `어니언` + 지역 `성수` → `어니언 성수` 확정. **지역이 없으면 거부**

## 축 설계 원칙

### 값을 미리 정해둡니다 (종류·위치 제외)

AI가 값을 자유롭게 만들게 두면 재현되지 않습니다.

| | 재현성 | 근거 |
| --- | --- | --- |
| `상황` — 값을 모델이 자유 생성 | 4/10 | `데이트 ← "데이트"` (태그 한 단어) |
| `예약·대기` — 값 4개로 고정 | 9/10 | 실제 문장 |

닫힌 어휘가 세 군데서 이득입니다: 스키마 `enum`이 잘못된 값을 API 단계에서
막고, 판단이 서술이 아니라 분류 문제가 되고, **어떤 문장을 찾아야 하는지가
정해지니 수집도 겨냥할 수 있습니다** (`booking` 프로브가 그렇게 생겼습니다).

`종류`와 `위치`는 열어둡니다 — 세상에 있는 업종이 어떤 목록보다 많습니다.

### 좋은 축은 반쯤 참입니다

10곳에서 근거가 잡힌 비율입니다. **5/10에 가까울수록 쓸 만하고, 10/10은
쓸모가 없습니다.**

```
영업시간  9/10 ← 너무 흔함, 축이 아니라 카드 필드로
예약 표기  7/10      혼밥  5/10      주차  5/10 ← 신규 후보
웨이팅    3/10      룸    2/10 ← 너무 드묾
단체 가능 10/10 ← 폐기
```

### 폐기한 축들

**`상황`** (데이트·모임·기념일) — 리뷰어 한 명의 의견을 태그 목록에서 읽었습니다.
재현성 4/10.

**`가격대`** — 구간 계산이 모델의 `isMain` 플래그에 의존했고 그 플래그가 실행마다
달라졌습니다. 하동관에서 수육(대) 60,000원이 곰탕 18,000원을 밀어냈습니다.
8곳 중 7곳은 맞았으니 **되살릴 값어치가 있습니다** — 지금 구조에서는 근거 문장이
남아 검사할 수 있습니다.

**`인원`** (혼밥·단체·소규모) — 넣고 같은 날 뺐습니다. `단체 가능`이 10곳 중
10곳에서 참이었고, **발췌를 늘리자 오히려 악화**됐습니다(7/10 → 10/10). 근거가
많아지면 "단체" 언급을 찾을 확률이 올라가니까요. 틀린 게 아니라 서울 식당
대부분이 실제로 참이어서, 모든 카드에 붙는 라벨은 필터가 될 수 없습니다.

## 모델 선택 — DeepSeek을 왜 안 쓰는지

`deepseek-v4-flash`를 붙여서 두 단계 모두 재봤습니다. 배선은 남아 있고
`TRUN_ON_JUDGE_DEEPSEEK=1`로 켤 수 있습니다.

### 수집에는 못 씁니다 — 한국 사이트를 검색하지 못합니다

한국 가게를 물으면 중국·대만 여행 사이트만 돌아옵니다
(`qa.trip.com`, `cn.trippose.com`, `koreatriptips.com/zh-tw`). 다이닝코드·식신·
네이버는 한 번도 나오지 않았습니다. 다음을 전부 시험했고 전부 실패했습니다:

- Responses API에 `allowed_domains` → 에러 없이 **빈 응답**
- Anthropic 호환 엔드포인트(`/anthropic/v1/messages`)에 `web_search_20260209`
  + `allowed_domains`(한국 6곳) + `user_location: KR` → 파라미터를 **받기만 하고 무시**
- 구버전 툴 타입 `web_search_20250305` → 17건 전부 해외 사이트
- `site:diningcode.com` 연산자 → **결과 0건**
- 프롬프트로 "한국어 페이지만 인용" → 효과 없음
- URL 직접 지정 → **fetch 도구가 없습니다** (모델이 그렇게 답합니다)

### 판단에서도 졌습니다 — 추론 토큰을 14배 씁니다

9곳 × 3회, 동일한 발췌로 비교했습니다.

| | Luna | DeepSeek |
| --- | --- | --- |
| 재현성 | 7/9 | 7/9 |
| 근거 검증 | 12/12 | 11/11 |
| 시간 | **2.6초** | 19.4초 |
| 추론 토큰 | **113** | 2,241 |
| 건당 비용 | **$0.0006** | $0.0009 |

출력 단가가 4.3배 싼데 토큰을 14배 써서 **결과적으로 더 비쌉니다.** 화육계에서는
추론 토큰이 5,824개까지 갔습니다.

그리고 **판단은 전체 토큰의 3%뿐**입니다 (판단 입력 1,149 vs 수집 입력 58,000).
여기서 모델을 바꿔 아낄 수 있는 금액은 애초에 작습니다.

### 그래도 알아둘 DeepSeek 특성

- **이미지 입력을 조용히 버립니다.** `input_image`가 에러 없이 자리표시자
  텍스트로 치환됩니다. 분석 경로를 옮기면 실패가 아니라 **그럴듯한 헛소리**가
  돌아옵니다.
- **도구를 쓸 때 `json_schema`를 지키지 않습니다.** 산문 + ` ```json ` 펜스로
  답하고, `output`에 나레이션 message가 10개씩 들어옵니다. 첫 message를 읽으면
  `"I'll search for this place."`를 읽게 됩니다. 파서는 전체를 이어붙여
  펜스·중괄호 균형으로 객체를 찾습니다.
- **`effort: none`은 쓸 수 없습니다.** 추론 토큰 0으로 35% 빠르고 32% 싸지만
  재현성이 1/4로 붕괴하고, 프롬프트가 금지한 웨이팅 오분류가 되살아납니다.
- 컨텍스트 캐시가 자동이고 히트가 50배 쌉니다($0.0028 vs $0.14). 고정 프롬프트를
  앞에 두면 80~90% 히트합니다.
- 오프피크 16:30~00:30 GMT(한국 01:30~09:30)에 최대 50% 할인. 배치 재보강용.

## 출처 접근 정책 — 무엇을 긁을 수 있나

`robots.txt`와 실제 서버 반응을 각각 확인했습니다. **둘이 다릅니다.**

| 소스 | robots.txt | 실제 |
| --- | --- | --- |
| 다이닝코드 | 학습 봇만 차단(GPTBot·ClaudeBot). `OAI-SearchBot` 언급 없음 = 허용 | Luna가 편의시설 필드까지 읽어옴 |
| 네이버 지도 · 카카오맵 | `AI TRAINING AND RAG IS STRICTLY PROHIBITED` 명시 | — |
| m.place.naver.com | `Disallow: /` 전면 | — |
| blog.naver.com · cafe.naver.com | 검색 봇까지 차단(`OAI-SearchBot` 포함) | Luna가 일부 닿긴 하나 색인이 부실 |
| 식신 | AI 차단 조항 **없음** | **CloudFront가 비브라우저를 403** (Jina Reader도 막힘) |

다이닝코드 주석이 이 구도를 정확히 설명합니다 — *"AI 모델 무단 학습 차단
(검색 인덱싱/트래픽 유입은 유지)"*. **모델 제공사의 검색 봇으로 읽는 건 허용,
우리가 직접 크롤링하는 건 아님**이 현재 지형입니다.

그래서 우리는 긁지 않고 `web_search`를 씁니다. `filters.allowed_domains`가
실제로 지켜지는 것을 확인했습니다(다이닝코드만 허용 → 다이닝코드만 인용).

## 남은 문제 — 수집 재현성

**아직 안 고친 유일한 병목입니다.**

같은 질의를 두 번 던지면 발췌가 **19~46%만 겹칩니다.**

```
밍글스 22%   방콕테이블 19%   화육계 28%   하동관 41%   삼원가든 46%
```

판단이 이 흔들림을 상당히 흡수합니다(같은 사실을 다른 문장으로 만나도 같은
라벨). 하지만 근거가 한 곳에만 있는 가게는 놓칩니다:

```
방콕테이블  1회차  발췌 11건 · 대기 근거 0건 → 웨이팅 없음
           2회차  발췌 14건 · 대기 근거 1건 → 웨이팅 있음
      ★ "용산 해방촌에서 줄서는식당, 웨이팅이 있는 식당으로 이미 유명한"
```

**근거가 오면 판단은 정확합니다.** 수집이 반만 잡습니다.

### 해결 방향

발췌를 버리지 말고 **가게 단위로 쌓는 것**입니다. 스크래치패드에서 수집 2회를
합집합으로 두었을 때 재현성이 4/10 → 9/10으로 올랐습니다. 세 방식이 있습니다.

| | 쌓는 곳 | 대가 |
| --- | --- | --- |
| 절충 | 안 쌓음. 한 요청에서 수집 2회 후 합집합 | +10초, 수집비 2배. 코드 변경 최소 |
| A | 서버에 가게 단위 캐시 | 서버에 상태가 생김. 재설치·기기 교체에도 남음 |
| B | 앱이 기존 발췌를 함께 전송, 서버가 합쳐 반환 | 서버 무상태 유지. 앱 스키마 변경 |

A와 B는 두 번째 조회부터 공짜입니다. 절충으로 효과를 먼저 확인하는 순서를
권합니다.

4. **카카오 로컬 API 키** — 장소 특정을 더 단단하게. 무료, 카드 불필요
5. **analyze 분리** — Luna는 화면 전사만, DeepSeek이 분류·요약·구조화.
   판단 단계에서는 DeepSeek이 졌지만 그건 출력이 짧은 작업이었고, 이쪽은
   출력이 길어서 계산이 반대로 나올 수 있음
