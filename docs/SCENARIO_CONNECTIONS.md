# 시나리오 연결 계약

실제 이미지 분석 응답을 이용한 변형 사례와 회귀 검증은 [이미지 기반 시나리오 변형 검증](SCENARIO_VARIATIONS.md)에 정리했다.

레시피, 맛집, 패션, 뷰티, 여행, 생활 꿀팁, 쇼핑, 건강·운동은 각자 독립된 활동 보드와 근거 그래프를 유지한다. 연결은 두 보드의 결과를 합쳐 사실로 승격하는 명령이 아니다. 사용자가 두 활동을 함께 보겠다고 확인한 관계이며, 상대 보드로 이동하고 현재 할 일과 확정 결과의 존재 여부를 볼 수 있게 한다.

## 관계와 방향

| 관계 | 시작 → 대상 | 의미 |
| --- | --- | --- |
| `recipe_shopping` | 레시피 → 쇼핑 | 레시피를 위한 장보기 |
| `recipe_health` | 레시피 → 건강·운동 | 식사와 운동 계획 |
| `travel_dining` | 여행 → 맛집 | 여행 중 고려할 식당 |
| `travel_life_tip` | 여행 → 생활 꿀팁 | 여행 준비에 쓸 팁 |
| `fashion_beauty` | 패션 → 뷰티 | 함께 준비할 코디와 루틴 |
| `fashion_shopping` | 패션 → 쇼핑 | 코디를 위한 상품 비교 |
| `beauty_shopping` | 뷰티 → 쇼핑 | 루틴을 위한 상품 비교 |
| `shopping_life_tip` | 쇼핑 → 생활 꿀팁 | 구매 판단에 쓸 팁 |
| `health_life_tip` | 건강·운동 → 생활 꿀팁 | 운동 실천에 쓸 팁 |
| `related` | 서로 다른 두 시나리오 | 특정 인과관계를 주장하지 않는 일반 연결 |

UI에서는 양쪽 보드에서 같은 연결을 볼 수 있다. 관계의 방향은 그래프에 보존한다. 지원되는 명명 관계가 없는 조합은 `related`로 연결한다. 같은 시나리오 유형끼리는 이 계약에서 연결하지 않는다.

## 그래프 저장과 갱신

보드마다 `scenario.activity` 앵커를 두고, 연결마다 `scenario.connection` 엔터티를 둔다. `scenario.connection_from`, `scenario.connection_to`, `scenario.connection_kind` 세 assertion은 사용자가 연결을 확인한 `user_confirmation` 소스의 동일한 evidence를 참조한다. 보드 ID는 앵커의 `externalIds.activityId`에 저장한다. 그래프 엔터티의 식별은 보드 ID와 사용자의 조합으로 결정하므로 서로 다른 사용자의 앵커는 합쳐지지 않는다.

레시피·선택한 식당·코디·뷰티 루틴·여행 일정·생활 실천 계획·쇼핑 선택·운동 계획이 사용자 확인을 거쳐 생성되면, 연결 엔터티에서 그 결과 엔터티로 `scenario.connection_from_subject` 또는 `scenario.connection_to_subject`를 추가한다. 연결을 먼저 만들고 결과를 나중에 확정해도 동일하게 추가한다. 이 간선은 연결 확인 근거와 결과 자체의 근거를 함께 요구한다. 어느 한쪽 근거가 사라지면 확정 결과 연결을 표시하지 않는다. 예를 들어 쇼핑 보드와 레시피 보드를 연결해도 재료를 구매했다는 주장은 생성하지 않는다. 맛집 보드와 여행 보드를 연결해도 방문했다는 주장은 생성하지 않는다. 실제 구매·방문·운동 여부는 각 시나리오의 별도 보고 작업에서만 남긴다.

원본 캡처나 시나리오 확인 소스가 삭제되어 보드가 지워지면 연결의 확인 소스도 삭제하고, 간선의 근거를 무효화한다. 해당 보드 앵커의 제목과 외부 ID도 지운다. 반대편 보드는 보존한다. 사용자가 연결만 해제할 때도 연결 소스와 간선 근거를 삭제한다. 읽기는 활성 소스·간선·소유자를 확인한 연결만 반환한다.

## API와 보드

`GET /v1/kernel/scenario-connections/{activityId}`는 연결된 보드의 현재 제목, 시나리오, 실행 가능한 작업 수, 확정된 핵심 결과를 반환한다. `POST /v1/kernel/scenario-connections`는 양쪽 보드 ID·revision, 관계 종류, `confirmed: true`, 재시도용 command ID를 요구한다. 다른 사용자의 보드, 미승인 계획, 오래된 revision, 같은 관계의 중복은 거절한다. `POST /v1/kernel/scenario-connections/delete`는 특정 연결을 해제한다. 모두 기존 커널 토큰으로 보호한다.

연결은 독립 보드의 작업 완료 조건이나 데이터 바인딩을 자동으로 바꾸지 않는다. 한 보드의 결과가 다른 보드의 task input으로 쓰이려면 별도 계획 제안과 근거 재검토가 필요하다. 이는 연결 관계만으로 재고·소유·예약·구매·방문 등의 상태를 추론하지 않기 위한 경계다.

`recipe_shopping` 관계를 쇼핑 보드에서 조회하면, 레시피 보드의 `calculate_requirements` 작업이 완료된 경우 `recipeNeeds` 읽기 전용 투영을 함께 반환한다. 투영에는 계산 결과 ID, 목표 인분, 각 재료의 `requiredQuantity`·`availableQuantity`·`missingQuantity`·상태가 들어간다. 미완료이면 `not_ready`, 레시피 맥락·결과·근거가 바뀌었으면 `stale`만 반환해 과거 수량을 숨긴다. 캡처나 연결 소스를 삭제하면 관계 자체가 조회에서 사라진다. Flutter 쇼핑 보드는 이 목록을 보여주되 상품과 재료의 동일성, 상품 몇 개를 사야 하는지, 구매 여부는 판단하지 않는다. 사용자는 새로고침으로 최신 계산 결과를 다시 읽을 수 있다.

`ready`는 현재 활성 레시피의 그래프 관계가 온전하고, 계획에 묶인 레시피 본문·revision·목표 인분과 완료된 계산 결과가 모두 일치할 때만 반환한다. 재료를 정정하면 기존 계산 결과는 남겨 두되 연결 조회에는 `stale`만 돌려준다. 이미 계산을 완료한 보드는 시작된 작업을 덮어쓸 수 없으므로 새 레시피 활동에서 계획을 승인하고 다시 계산해야 한다. 쇼핑 화면은 연결을 새로고침하는 동안에도 캐시된 수량을 숨기고, 조회 실패 시 `unverified`로 유지한다.

쇼핑 보드의 **후속 레시피로 연결 옮기기**는 `GET /v1/kernel/scenario-connections/transfer-review/{connectionId}`로 해당 레시피의 승인된 직접 후속 활동과 최신 필요량을 조회한다. 필요량 계산을 완료한 후속 활동만 선택할 수 있다. 사용자가 새 재료량을 확인하고 `POST /v1/kernel/scenario-connections/transfer`를 보내면 서버는 원래 연결의 근거 소스를 삭제하고 새 연결·간선을 하나의 트랜잭션에서 만든다. 기존 연결과 새 연결이 함께 유효한 중간 상태는 저장하지 않는다. 검토한 양쪽 revision과 새 계산 결과 ID를 재검증하며, 같은 command ID로 재시도해도 결과는 한 번만 적용한다. 이미 시작된 쇼핑 선택 작업과 다른 레시피의 후속 활동은 거절한다. 이 명령은 쇼핑 계획의 레시피 결과 참조를 바꾸지 않는다. 사용자는 이어서 **쇼핑 계획에 반영 검토**와 보드의 변경안 승인을 거쳐야 한다.

쇼핑 보드에서 `ready`인 연결의 **쇼핑 계획에 반영 검토**를 누르면 서버가 기존 계획에 참조된 계산 결과와 새 결과를 비교해 재료별 추가·제외·필요량 변경을 보여준다. 사용자가 `POST /v1/kernel/shopping/recipe-needs/proposals`로 변경안을 만들 때 비교 화면에서 받은 `expectedSourceResultId`도 제출하므로, 그 사이 재계산됐다면 제안이 거절된다. 보드에서 따로 승인하면 아직 시작하지 않은 `confirm_choice` 작업에 레시피 계산 결과의 연결 ID·결과 ID·레시피 revision만 저장한다. 재료 수량이나 상품 동일성 판단을 쇼핑 계획에 복사하지 않는다. 제안 승인과 상품 선택 시 서버가 연결·근거 그래프·계산 결과의 최신성을 재검증한다. 레시피가 다시 바뀌거나 연결이 삭제되면 쇼핑 보드가 변경 검토 상태가 되고, 오래된 참조로 상품을 선택할 수 없다. 상품 선택이 시작된 쇼핑 작업은 입력을 바꾸지 않으며 새 쇼핑 활동에서 다시 확인해야 한다.

레시피가 계획에 연결된 쇼핑 활동에서 상품을 고를 때는 그 상품이 어느 필요 재료에 해당하는지 사용자가 선택하거나 **확인하지 않음**을 명시해야 한다. 서버는 최신 레시피 계산 결과에 실제로 포함된 재료 ID만 수락한다. 확인한 경우 `shopping.choice_matches_ingredient` 간선을 선택한 상품의 `shopping.purchase_choice`에서 해당 `recipe.ingredient`로 기록하고, 사용자 확인·상품 제목·레시피 재료 항목의 근거를 함께 묶는다. 선택 결과에도 판단과 당시 계산 결과 ID를 남긴다. 미확인이면 간선을 만들지 않는다. 이 관계는 **선택 당시 사용자가 확인한 상품과 재료의 대응**이며 상품의 전역 동일성, 필요한 상품 개수, 구매 완료를 뜻하지 않는다. 근거 변경 후에는 현재 쇼핑 계획이 다시 검토 대상이 되고, 과거 선택 결과를 새 계획으로 복사하지 않는다.

재료 대응을 확인한 선택에서는 상품 **한 개의 포장 분량**도 사용자가 입력하거나 미확인으로 남긴다. 확인한 값은 `shopping.package_quantity`에 사용자 확인 근거와 함께 기록한다. 서버는 사용자가 고른 상품 개수와 포장 분량을 곱한 뒤, 레시피 결과의 `missingQuantity`가 확정되어 있고 같은 차원의 단위일 때만 부족량의 충족 여부를 계산한다. `g`/`kg`, `ml`/`l`처럼 명확한 변환만 허용하며 질량과 부피, 티스푼과 테이블스푼, 재료 밀도는 추정하지 않는다. 재고 또는 포장 분량이 미확인이거나 단위가 호환되지 않으면 판단 불가 상태로 남긴다. 이 계산은 선택한 수량의 비교일 뿐 구매나 재고 추가를 뜻하지 않는다.

새 장보기 묶음 경로에서는 여러 재료에 상품을 따로 선택하고, 한 재료의 여러 상품 분량을 합산한다. 선택하지 않은 재료도 `unselected`로 결과에 남긴다. 각 상품의 구매 여부는 독립적으로 보고하며, 실제 재고는 그 뒤 사용자가 별도 관측한다. 이미지에서 보이는 포장 분량을 선택한 경우 그 캡처의 근거 ID만 제출할 수 있다. 레시피가 정정되면 묶음 결과를 덮어쓰지 않고 `basket-review`에서 현재 필요량과의 차이를 읽는다. 새 계산이 없으면 오래된 양을 표시하지 않는다.
