# 첫 맛집 시나리오: 저장한 식당을 지점까지 확인하고 방문하기

상태: 첫 수직 흐름 구현 중. 아래는 목표 계약이며, 실제 구현 범위와 미완성 항목은 마지막의 **현재 구현 범위**를 따른다.

## 사용자가 이루려는 일

> “토요일 저녁에 성수에서 두 명이 식사하려고 한다. 예전에 저장한 맛집 중 한 곳을 정하고, 방문 전에 필요한 정보를 확인한 뒤, 실제로 갔는지 기록하고 싶다.”

입력은 식당을 소개하는 **실제 이미지 캡처**에서 출발한다. 앱은 이미지를 분석해 출처가 있는 정보를 저장한다. 사용자가 만든 식사 활동은 그 자료를 다시 찾고, 식당의 **정확한 지점**을 골라 방문까지 이어간다. 첫 시나리오의 성공은 추천 문구의 그럴듯함이 아니라, 다른 지점을 섞지 않고 저장 자료에서 실제 행동으로 연결되는지로 판단한다.

### 검증용 예시

가상 데이터로 다음 네 캡처를 만든다. 실제 영업 정보나 주소로 오인되지 않도록 모든 테스트 화면에 `합성 자료` 표식을 둔다.

| 캡처 | 이미지에 보이는 것 | 의도 |
| --- | --- | --- |
| A | `모퉁이식당 성수점`, `성수`, 대표 메뉴 | 성수 지점 후보 |
| B | `모퉁이식당 연남점`, `연남`, 대표 메뉴 | 같은 브랜드의 **다른** 지점 |
| C | `모퉁이식당 성수점`, `성수`, 다른 게시물 | A와 같은 지점에 관한 두 번째 출처 |
| D | `성수국수집`, `성수`, 대표 메뉴 | 비교할 수 있는 다른 성수 식당 |

사용자는 “토요일 19시, 성수, 2명” 활동을 만든다. A와 C는 각각의 캡처와 근거를 보존한 채 같은 지점에 연결될 수 있고, B는 별개 지점으로 남는다. 후보에는 A/C로 뒷받침되는 지점과 D가 각각 한 번씩 나타나며 B는 지역 조건에서 빠진다. 사용자가 한 지점을 선택하고 지도 링크를 연 뒤, 방문 여부를 직접 기록한다. 지도 링크를 열거나 예약 사이트로 이동했다는 이유만으로 방문·예약 완료로 기록하지 않는다.

## 화면에서 일어나는 순서

1. **캡처 저장·분석.** 이미지가 `/v1/analyze`로 전송된다. `contentKind=place`, `place.name`, `place.searchArea/address`, `category`, 보이는 메뉴·특징 등의 `facts`, 각 필드의 `evidenceIds`를 받는다. 사진만으로 보이지 않는 영업시간·예약 상태·좌표는 만들지 않는다.
2. **사용자 확인.** 추출한 상호·지역·지점·분류를 원본 이미지 옆에서 수정하거나 “식당을 특정할 수 없음”으로 남긴다. 확인된 분석만 `/v1/kernel/ingestion/reviewed-capture`로 가져온다. 확인은 *이미지에서 무엇을 읽었는지*에 대한 확인이며, 실제 지점 신원·현재 영업 정보의 보증이 아니다.
3. **지점 식별.** 장소 검색 결과는 후보로만 받는다. 캡처의 지점명과 주소가 있으면 둘 다 일치하고 결과가 하나일 때만 자동 연결을 제안한다. 지역어만 있거나 같은 상호의 여러 지점이 남으면 사용자에게 후보를 보여주고 명시적 선택을 받는다. 검색 실패에도 캡처는 남고 텍스트 검색·지도 열기는 가능하다.
4. **활동 생성.** 사용자가 시각, 지역, 인원을 입력한다. 서버는 확인된 지점과 출처를 검색해 후보 집합을 만들고, 계획 변경안을 제시한다. 사용자가 승인해야 TaskBoard에 작업이 생긴다.
5. **후보 비교·선택.** 후보가 둘 이상이면 지역 적합성, 사용자가 저장한 메뉴, 예약·대기처럼 **근거가 있고 현재성 조건을 만족하는** 정보만 비교한다. AI는 주어진 후보 ID와 근거로 설명을 작성할 수 있지만, 새 식당이나 사실을 만들 수 없다. 모르는 축은 `확인 필요`로 표시한다. 최종 선택은 사용자가 한다.
6. **방문 준비.** 선택 지점의 주소·지도 링크·저장한 원본을 보여준다. 방문 시각에 중요한 영업·예약·대기 정보는 새 근거가 없으면 미확인으로 둔다. 예약 링크 열기는 `준비`일 뿐이고, 확인 번호와 근거가 있어야만 `예약 확정`으로 기록한다.
7. **결과 기록.** 사용자가 `다녀왔어요 / 못 갔어요 / 아직 몰라요` 중 하나를 고른다. `다녀왔어요`일 때만 방문 시각과 선택 지점을 연결한 방문 기록을 만든다. 나머지 상태는 방문 사실로 승격하지 않는다.

## 지식 그래프 계약

| 층 | 저장할 것 | 지켜야 할 경계 |
| --- | --- | --- |
| 캡처 | 캡처마다 `Source → SourceVersion → Evidence`; 제목·장소·메뉴 문구를 `ingestion.extracted_field` | 이미지에서 읽은 **원문 시점의 주장**. 현재 영업 상태가 아님 |
| 언급 | 캡처마다 `dining.place` Mention | 상호명이 같다는 이유로 Entity를 자동 합치지 않음 |
| 지점 | 실제 방문할 수 있는 지점별 `dining.place` Entity; 검증된 제공자 ID와 주소 | 브랜드와 지점을 구별. 외부 ID도 지점 신원 결정의 근거를 보존 |
| 연결 | Mention → IdentityDecision → 지점 Entity | A/C는 같은 지점으로 연결 가능, B는 별개. 거부·철회 가능 |
| 장소 정보 | 주소·메뉴·예약/대기 등 필드별 Assertion/Resolution | 출처·관측시각·유효기간·근거를 가진 값만 표시. 충돌·오래됨·미확인을 구분 |
| 활동 선택 | `select_place`의 버전 있는 TaskResult가 `placeId`와 선택 당시 근거를 보유 | 선택은 활동 결정이다. 장소의 영구 속성으로 복제하지 않음 |
| 방문 | 사용자 확인의 `dining.visit` Entity와 `dining.visited` 관계 | 지도 열기, 위치 근접, 예약 준비만으로 방문 관계를 만들지 않음 |

현행 가져오기는 `dining.place` Mention까지만 만든다. 맛집 구현에서는 확인된 Mention의 지점 연결과, 캡처의 지원 필드를 근거 있는 dining 주장으로 승격하는 **명시적 매핑**이 필요하다. `facts`의 자유 텍스트를 임의의 현재 상태 슬롯에 일괄 복사하지 않는다. `searchArea`는 검색 힌트이고 검증된 주소가 아니다. 예약·대기처럼 바뀌는 값은 현재성 기한을 둔다. 새로운 캡처가 들어와도 이전 원본과 Assertion은 남겨 두고 Resolution을 다시 계산한다.

삭제 시 출처에 종속된 Assertion과 신원 연결의 근거를 철회하고, 선택 활동의 `pendingChanges`를 기록한다. 다른 독립 근거가 남아 있으면 장소 Entity 자체를 무조건 삭제하지 않는다. 이미 완료한 방문 기록도 조용히 바꾸지 않고 당시의 사용자 기록과 출처 상태를 구분한다.

## TaskBoard 계약

작업 ID는 화면 문구와 무관하게 안정적으로 둔다. 첫 계획의 실행 순서는 다음과 같다.

```text
compare_candidates? ──→ select_place ──→ verify_visit_details ──→ record_visit_outcome
                            │                        │
                            └──── 지도·원본 열기     └──── 예약 준비/확인은 조건부
```

| 작업 | 실행 주체·입력 | 완료 결과 |
| --- | --- | --- |
| `compare_candidates` | 시스템/AI; 확정된 지점 ID, 활동 조건, 근거 스냅샷. 후보가 하나면 생략 | 후보별 이유·미확인 축·근거 ID가 있는 비교안. 추천은 선택이 아님 |
| `select_place` | 사용자; 비교안 또는 단일 후보 | 정확한 `placeId`, 선택 시각, 선택 당시 근거 버전 |
| `verify_visit_details` | 사용자 또는 신뢰 가능한 외부 조회; 선택 지점, 방문 시각 | 확인한 주소·시간·예약/대기 상태와 출처, 또는 명시적 `unknown`. 미확인도 지도 열기·방문을 막지는 않음 |
| `prepare_reservation` (조건부) | 사용자; 실제 예약이 필요하다고 결정한 경우 | 링크·방법을 확인했다는 준비 상태. 예약 완료 아님 |
| `confirm_reservation` (조건부) | 사용자/신뢰 가능한 연동; 확인 번호와 증거 | 검증된 확정 상태. 링크 열기만으로 완료 불가 |
| `record_visit_outcome` | 사용자; 선택 지점과 결과 | `visited / not_visited / unknown`; `visited`일 때만 방문 관계 생성 |

`verify_visit_details`의 결과를 고치거나 새 캡처가 선택 지점의 사실과 충돌하면 후속 작업을 재검토 대상으로 표시한다. 이미 시작·완료된 작업의 소비 입력과 방문 결과는 새 값으로 몰래 덮지 않는다. 사용자가 지점을 바꾸면 새 계획 revision으로 뒤 작업을 다시 연결한다. 비교·선택에는 `ContextSnapshot`의 readSet과 빈 검색을 포함한 queryWatch를 걸어, 새 지점이 나타나거나 기존 지점 근거가 바뀌면 오래된 계획 승인을 거부한다.

## 첫 구현에서 분리할 범위

- **필수:** 실제 이미지 분석 → 확인 가져오기 → 지점 식별/수정 → 활동 후보 조회 → 지점 선택 → 지도·원본 열기 → 사용자 방문 결과. 이는 첫 레시피와 같은 이미지→API→커널→보드의 수직 검증이다.
- **조건부:** 후보가 복수일 때의 근거 있는 비교, 예약 준비와 증거 기반 예약 확정. 기존 dining pack의 `compare_places`, `prepare_reservation`, `confirm_reservation`, `record_visit`는 계약 선언만 있으며 실행 어댑터나 시나리오 API가 구현된 것으로 취급하지 않는다.
- **후속:** 자동 예약 실행, 실시간 대기 번호, 위치 기반 자동 방문 판정, 지오펜스 알림, 상시 영업시간 수집. 첫 시나리오의 성공 조건에 넣지 않는다.

## 검증과 완료 조건

| 사례 | 기대 결과 |
| --- | --- |
| A~D의 식당 캡처 PNG를 각각 실제 `/v1/analyze`에 전송 | 장소 분류·상호·지역·보이는 사실과 근거를 반환; 원본에 없는 사실은 없음. 각 실제 응답을 fixture로 보관 |
| A와 C의 같은 지점, B의 다른 지점, D의 경쟁 후보 | A/C의 출처는 각각 남고 후보는 하나; B는 합쳐지지 않으며 성수 후보에서 빠짐; D는 독립 후보 |
| 이름만 같고 주소/지역이 애매함 | 자동 확정하지 않고 사용자에게 선택 또는 미해결 상태 제공 |
| 검색 결과 없음·외부 API 실패 | 캡처와 활동은 보존; 텍스트 지도 검색과 재시도 가능 |
| 오래된 예약 정보·서로 다른 영업시간 | `확인 필요`/충돌로 표시; 예약·영업 확정 문구 금지 |
| 새 캡처 추가·기존 출처 삭제·지점 수정 | 영향 받은 활동의 변경 표시와 재검토; 과거 TaskResult 불변 |
| 같은 명령 재전송·앱/서버 재시작 | 활동·선택·방문 기록 중복 없음 |
| 지도 열기, 예약 페이지 열기, 방문 안 함 | 방문·예약 확정 Assertion 생성 안 함 |

검증은 두 층으로 나눈다. A~D 합성 이미지 **각각**을 실제 API 서버에 보내 응답을 보관하고, 가짜 장소 검색 결과로 지점 충돌·상태 전이를 반복 테스트한다. 합성 가게는 외부 장소 제공자에 실제로 존재하지 않으므로, 가짜 지점을 실제 카카오 검색으로 찾은 것처럼 기록하지 않는다. 실장소 연동을 시험할 때는 별도의 실제 공개 장소 자료와 제공자 응답을 사용한다.

## 현재 구현 범위 (2026-09-26)

- 실제 `/v1/analyze`에 합성 식당 이미지 A~D를 각각 전송해 받은 응답을 `server/test/fixtures/dining_*_live_analysis.json`에 보관했다. 이미지는 같은 위치의 PNG다. 첫 D 이미지에서는 한 글자를 잘못 읽어, 원본 글자를 더 명확히 만든 뒤 다시 전송했다. 분석은 사용자 확인 이전의 관측값일 뿐이다.
- 확인되어 서버에 가져온 식당·카페 캡처를 지역으로 거르고, 상호·지역·주소 키가 같은 자료를 **임시 후보**로 묶는다. 승인 대기 계획은 `select_place → review_visit_details → record_visit_outcome`의 고정 작업 세 개로 만든다. 사용자가 후보를 선택할 때만 Mention의 IdentityDecision을 수락하고, 기존에 연결된 동일 Entity는 재사용한다. 외부 장소 제공자 검증은 아직 하지 않으므로 이 Entity는 **사용자 선택 지점**이지 검증된 제공자 지점이 아니다.
- 개발용 Flutter 보드는 캡처 선택, 지역·시각·인원 입력, 계획 승인, 원본 캡처·지도 열기, 지점 선택, 방문 결과 기록을 제공한다. 지도는 상호·지역 텍스트 검색이며 좌표나 주소가 검증됐다는 뜻이 아니다. 방문 전 상세 정보 작업은 현재 `unknown`만 기록한다. `visited`에만 사용자 보고 Source/Evidence와 방문 Assertion을 만든다.
- 캡처 삭제 시 현재 구현은 그 출처를 사용한 맛집 활동을 함께 제거하고 명령 영수증을 tombstone 처리한다. 위에서 설명한 `pendingChanges` 기반의 부분 재검토와 독립 근거 유지 정책은 아직 구현되지 않았다.
- 후보 비교 AI, 제공자 지점 조회·대조, 검증된 주소/영업/예약 정보, 예약 작업, 변경된 선택의 재계획은 후속 구현이다. 이 항목을 현재 보드의 확인된 사실로 표시하지 않는다.

## 남은 코드 간극

1. `dining`의 맛집 시나리오 생성 API와 앱 TaskBoard의 기본 흐름은 연결됐으나, 후보 비교 실행기는 없다.
2. `/v1/resolve-place`는 이름·주소를 받지만 `searchArea`를 직접 받지 않는다. 지역어만 보이는 캡처의 지점 확인 규칙과 사용자 선택 UI가 필요하다.
3. 사용자가 후보를 선택할 때 Mention을 장소 Entity에 연결한다. 캡처의 지원 필드를 근거 있는 dining Assertion으로 변환하는 작업과 제공자 지점 확인은 남아 있다.
4. 기존 계획함과 새 Activity Board는 양방향 동기화되지 않는다. 첫 시나리오에서는 새 보드에서 시작하고, 중복 계획을 자동 생성하지 않는다.
5. 예약 확정·방문 기록은 선언된 출력 형태만으로 진위를 보증할 수 없다. 확인 번호/근거와 사용자 입력 권한을 서버에서 검사해야 한다.
