# 이미지 기반 시나리오 변형 검증

전체 테스트의 읽는 순서와 분야별 범위는 [시나리오·이미지 검증 안내](TEST_VALIDATION_GUIDE.md)에 정리했다. 이 문서는 변형 사례의 세부 근거와 경계를 설명한다.

이 검증은 합성 캡처를 실제 `/v1/analyze` API에 보내 받은 응답을 보존하고, 그 응답을 테스트에서 재생한다. 합성 화면은 실제 매장·상품·건강 효과를 증명하지 않는다. 이미지와 응답은 `server/test/fixtures/variation_*`에 있고, `server/test/scenario_variations.test.js`가 이미지 SHA-256, 분석 스키마, 필드 근거, 보드 생성, 사용자 확정, 지식 그래프 연결과 삭제를 확인한다.

| 사례 | 분석 응답에서 확인된 정보 | 보드·그래프에서 지켜야 할 경계 |
| --- | --- | --- |
| 두부 달걀 볶음 + 두부 상품 | 두부 `300g`, 달걀 `2개`, 소금 `약간`; 상품 `2,400원` | 사용자가 소금을 `as_needed`로 확정한다. 4인분 환산 때 숫자를 만들지 않는다. 두 보드의 확정 결과를 연결하되 구매 사실은 만들지 않는다. |
| 두부·달걀 상품 장보기 묶음 | 별도 합성 달걀 상품 화면의 `달걀 10개입`, `4,900원` | 두 재료의 상품을 각각 고르고 소금은 비워 둔다. 달걀을 미구매로 보고하면 구매 관계를 만들지 않는다. 두부 구매 후 실제 보유량은 별도 확인해야 한다. |
| 이전 가격 + 현재 표시 가격 | `19,900원` 이전 표시가와 `12,900원` 화면 표시가가 각각 추출됨 | 사용자 확인 전에는 쇼핑 후보로 받지 않는다. 사용자가 화면 표시가를 고르면 별도 확인 근거로 연결하고, 이전 표시가는 선택할 수 없게 한다. 할인율·실제 결제액·구매 완료를 추론하지 않는다. |
| 제주 여행 + 성산읍 식당 | 여행 장소와 `제주 바다국수`, `제주 서귀포시 성산읍` | 사용자가 각각 일정과 식당을 확정한 후 `travel_dining`으로 연결한다. 일정과 식당 선택만으로 방문·예약을 만들지 않는다. |
| 패션 + 뷰티 | 기존 재킷·클렌저 이미지의 실제 API 응답 | 코디와 루틴을 별도로 확정하고 연결한다. 연결만으로 착용·제품 사용을 만들지 않는다. |
| 홈트 + 운동 준비 꿀팁 | 기존 홈트 응답과 새 꿀팁 화면의 순서 있는 `steps` 3개 | 생활 꿀팁의 `facts`/`steps` 두 표현을 화면 근거가 있을 때만 후보로 받는다. 연결만으로 운동 수행·꿀팁 실천을 만들지 않는다. |

생활 꿀팁 화면은 첫 실제 분석에서 `facts: []`, `steps: [1,2,3]`으로 나왔다. 기존 구현은 `facts`만 허용해서 이 캡처를 버렸으므로, 가져오기 단계에서 `life_tip.tip` 언급을 만들고 보드 후보는 근거가 붙은 연속 순서의 `steps`도 읽도록 수정했다. 단계의 원본 assertion을 철회하면 대기 중인 계획 승인이 `CONTEXT_STALE`로 실패한다.

기본 테스트는 모델 호출 없이 저장된 실제 응답을 재생한다. `cd server && npm test`로 실행한다. 분석 모델이 바뀌었을 때는 개발 서버를 켠 다음 `npm run test:scenario-variations-live`로 다섯 장의 새 이미지를 다시 분석한다. 새 응답을 검토하고 고정하려면 `npm run test:scenario-variations-live -- --record`를 사용한다. 이 명령은 의미와 근거 검사를 통과한 뒤에만 응답 파일을 갱신한다. 기존 패션·뷰티·여행·운동 이미지는 각 도메인의 `test:*image-live` 명령으로 재확인한다.

달걀 포장 화면은 `server/test/fixtures/variation_shopping_egg_pack.png`의 합성 이미지다. `npm run test:shopping-basket-image-live`가 실제 `/v1/analyze`에 보내 달걀 상품과 `4,900원` 가격 근거를 확인한다. `--record`는 검증을 통과한 응답만 `_live_analysis.json`으로 고정한다. 테스트는 두부·달걀 상품을 같은 장보기 묶음에 넣고 소금을 비워 둔 뒤, 두부만 구매했다고 보고하고 실제 보유량을 별도로 관측한다.

현재의 `scenario.connection_*_subject`는 **두 활동의 확인된 결과를 연결**한다. 두부 재료 요구량과 특정 두부 판매 상품이 같은 실물이라는 동일성, 여행 장소와 식당 사이의 거리·이동 시간, 상품 재고나 실시간 가격은 주장하지 않는다. 그런 주장이 필요해지면 별도의 근거·사용자 확인·갱신 규칙을 갖춘 관계로 추가해야 한다. 이전/현재 가격이 함께 보이는 화면은 `ingestion.reviewed_field`로 현재 표시 가격을 사용자가 확인한 뒤 쇼핑 보드 후보가 된다. 확인 근거가 철회·정정되면 그 근거로 만든 계획은 무효화된다.

연결된 쇼핑 보드의 `recipeNeeds`는 레시피의 `calculate_requirements` 결과를 읽기 전용으로 보여준다. 테스트에서는 4인분 환산 결과가 `두부 600g`, `달걀 4개`, `소금 필요한 만큼`으로 표시되고, 빈 재고 관측을 재고 0으로 해석하지 않아 `missingQuantity`는 `unknown`으로 남는다. 재료 근거를 철회하면 목록은 `stale` 상태만 반환하고 수량을 숨긴다.

쇼핑 후 실제 보유량을 확인하면 `recipe.observed_inventory`, `recipe.observes_inventory`, `shopping.inventory_after_choice` 관계와 사용자 보고 근거가 남는다. 이미 완료한 레시피 계산은 그대로 보존한다. 사용자는 레시피 화면에서 새 재고 확인 보드를 만들고 계획을 승인한 뒤, 연결된 **여러 쇼핑 보드**의 관측값 중 현재도 보유한 것만 재료별로 하나씩 선택한다. 같은 재료가 여러 보드에 있으면 충돌 후보로 보여주고 자동 합산하지 않는다. 선택한 관측값과 근거가 새 보드의 `check_inventory` 결과가 되고, `calculate_requirements`를 다시 실행하면 새 부족량이 나온다. 선택하지 않은 재료는 0개가 아니라 미확인이다. 관측 수량·근거 상품·선택한 근거 상품의 구매 상태·보드 연결·레시피 내용이 바뀌거나 관측이 취소되면 새 보드에 재검토가 표시되고, 이전 계산 결과는 기록으로 남는다. 취소 뒤 미실행 계산은 차단된다. 무관한 상품의 구매 상태나 실제 결제액만 정정하면 재고 계산은 무효화하지 않는다. 이 흐름은 `server/test/scenario_variations.test.js`에서 이미지 근거를 사용해 JSON 및 관계형 저장소 양쪽에서 검증한다.

이미지 API 경계는 `server/test/recipe_image_e2e.test.js`에서 실제 PNG를 로컬 `/v1/analyze`로 POST하고 바이트 해시·응답·보드 생성을 확인한다. 기본 테스트에서는 이미 기록한 모델 응답을 API 대역으로 재생하므로 유료 모델을 다시 호출하지 않는다. 실제 모델 회귀는 위의 `test:*image-live` 명령으로 별도로 검증한다. 실제 PostgreSQL은 `LUFFI_TEST_POSTGRES_URL`을 지정하고 `npm run test:postgres-real`로 마이그레이션, 재시작 후 조회, 동시 쓰기, 그래프 제약 실패 시 롤백을 검증한다.

레시피는 공통 아키텍처를 깊게 검증하는 첫 사례다. 쇼핑은 상품 선택·표시 가격·실제 결제·재고 관측의 구분, 패션은 소유·착용과 옵션 정정, 여행·맛집은 장소 동일성·거리·예약·방문 사실의 구분을 각자 별도 변형 시나리오와 이미지 API 재검증으로 확장해야 한다. 뷰티·운동·생활 꿀팁도 계획과 실제 사용·수행 사이의 경계를 독립적으로 검증한다. 공통 그래프·보드 계약을 재사용하되 도메인별 의미와 정정 규칙을 한 로직으로 강제하지 않는다.

쇼핑·패션·여행의 추가 회귀 검증은 각 도메인의 시나리오 테스트에서 JSON과 관계형 저장소 모두 실행한다. 쇼핑에서는 선택을 다른 상품으로 정정한 후 이전 상품의 `not_purchased`/`unknown` 결과를 새 구매로 뒤집는 요청을 거절한다. 이미 구매한 결과의 금액 정정과 기존 구매 이력은 별개로 남는다. 패션에서는 두 캡처를 사용자가 같은 상품으로 확인하더라도 같은 색상·사이즈의 단일 변형을 두 코디 자리에 중복 사용하지 못한다. 여행에서는 방문 보고가 끝난 뒤 일정 순서·시각을 정정해도 기존 방문 결과와 방문 그래프를 보존하고 새 활동으로 이어가도록 확인한다.

`server/test/cross_domain_image_pipeline.test.js`는 쇼핑·패션·여행·맛집 PNG 네 장을 실제 로컬 `/v1/analyze` HTTP 경로로 전송한다. 서버에 전달된 이미지 바이트의 해시를 확인한 뒤 이전에 기록한 모델 응답을 반환하고, 이 응답을 가져와 각 보드의 확정 작업과 여행↔맛집 연결까지 JSON·관계형 저장소 양쪽에서 실행한다. 표시 가격이 없는 패션 캡처는 쇼핑 후보에서 거절하고, 구매하지 않음·입지 않음·방문 미확인은 각각 구매·착용·방문 관계를 만들지 않는지 확인한다. 모델 자체의 새 출력은 별도의 `test:*image-live` 명령으로 검증해야 한다.

`server/test/wellbeing_image_pipeline.test.js`는 뷰티·홈트·운동 준비 꿀팁 PNG 세 장을 같은 이미지 API 경로에 보내 바이트 해시와 저장된 분석 응답을 대조한다. 사용자 확정과 운동↔꿀팁 연결 뒤에도 제품 사용·운동 수행·꿀팁 실천 관계를 만들지 않고, 미확인 결과 보고 역시 수행 관계로 승격하지 않는지 두 저장소에서 확인한다. `server/test/scenario_variations.test.js`는 실제 수행과 미확인을 섞어 보고한 뒤 연결된 꿀팁 캡처를 삭제해도 운동 수행 기록이 유지되는지 확인한다. 뷰티 루틴은 하나의 확인된 제품을 서로 다른 단계에서 재사용할 수 있으며, 단계별 사용 이력은 별도로 보존한다. 이 정정 경계는 `server/test/beauty_scenario_service.test.js`에서 확인한다.

실제 모델 재분석에서는 홈트 단계 라벨이 `1단계`와 `1단계 운동` 사이에서 달라졌지만 운동 내용과 근거는 같았다. 실시간 검증은 이 두 라벨을 허용한다. 제주 맛집 화면에서는 한 번의 응답에 메뉴 가격·안내 문구의 근거 ID가 빠져 있었다. 가져오기 로직은 이런 항목을 그래프에서 제외하며, 분석 지침은 근거를 붙일 수 없는 사실을 출력하지 않도록 강화했다. 장바구니 아이콘이 있는 클렌저 상세 화면을 일시적으로 일반 쇼핑 상품으로 분류한 경우도 있어, 사용 단계·제품 속성이 보이는 화장품 상세 정보는 `beauty_product`로 분류하도록 지침을 명확히 했다. 지침 버전을 올린 뒤 변형 이미지 다섯 장과 뷰티 이미지 두 장의 실제 분석이 다시 통과했다.
