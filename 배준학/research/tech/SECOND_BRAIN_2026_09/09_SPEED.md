# 09. 속도·비용: 캡처 → 기억을 2~3초에

> 조사일: 2026-09-29 · 원문: [`sources/09_speed_2026-09-29.md`](sources/09_speed_2026-09-29.md)
> 성격: 연구 자료 요약입니다. 작업 지시가 아닙니다. `[자체]` = 회사 발표 수치, `[추정]` = 직접 재야 하는 값. 비용은 1170×2532 스크린샷, 프롬프트 약 800토큰, 출력 200~400토큰 기준입니다.

## 결론

- **캡처당 약 20초의 주범은 추론 토큰과 긴 출력일 가능성이 큽니다(측정은 안 함).** OpenAI 지연 가이드에 따르면 출력을 50% 줄이면 지연이 약 50% 줄고, 입력을 50% 줄이면 1~5% 줄어듭니다.
- **추론은 한국어 정확도도 떨어뜨릴 수 있습니다.** KOCRBench에서 Gemini 2.5 Thinking이 212 → 184로 떨어졌습니다.
- **추론을 끄고, 출력을 제한하고, Flash-Lite·Luna급 모델로 바꾸면** 3초 이내, 캡처당 약 $0.001이 가능해 보입니다.
- **24시간 Batch 대신 Flex**를 쓰면 같은 가격에 몇 분 안에 끝납니다.

## 그래프 쓰기를 밀리초로

1. **이름 정규화:** NFKC, 공백·기호 제거, "…점"·"(주)" 제거 → `(user_id, type, norm_key)` 고유 키에 `ON CONFLICT`
2. **없으면 같은 사용자·같은 유형 안에서만 비교:**
   - `pg_trgm`
   - es-hangul 자모 분해 + 편집 거리, 초성
   - 사용자별 정확 벡터 검색
3. **판정:**
   - 유사도가 높고 주소·전화도 같으면 병합
   - 유사도가 낮으면 새 노드
   - 중간이면 `possible_same_as` 엣지 → 백그라운드 LLM
4. **동시성:** 트랜잭션 시작 시 `pg_advisory_xact_lock(hashtext(user_id))`. 모든 테이블에 `(user_id, …)` 복합 키
5. **다시 계획:** outbox → LISTEN/NOTIFY 또는 큐, 사용자별 1~2초 디바운스, 바뀐 엔티티에 연결된 할 일만

## 검색

- 사용자별 데이터는 작으므로 `user_id` B-tree + 정확 거리 계산으로 재현율 100%. 커지면 HNSW 반복 스캔.
- 한국어 키워드: ParadeDB + Lindera KoDic 2.8ms, `LIKE` + pg_trgm 12.9ms, mecab tsvector 96ms(긴 합성어 기준, ParadeDB는 AGPL)
- RRF로 SQL 안에서 결합
- 리랭커(bge-reranker-v2-m3 p95 215ms, Qwen3-Reranker-0.6B 약 400ms)는 **캡처 경로 밖**, 보드·검색에만

## 효과 대비 노력 순위

1. **추론 끄기 + 출력 200토큰 이하 + 짧은 JSON 키** — 효과 매우 큼, 몇 시간
2. **Flash-Lite / Luna 전환 + 이미지 축소** — 효과 큼, 비용 3~10배 절감, 하루 + 평가 세트
3. **병렬화**(캡처 동시 처리, OCR·업로드·임베딩 병렬) — 효과 큼, 쉬움. 요청 한도 확인
4. **Batch → Flex** — 쉬움
5. **SHA + dHash 중복 제거** — 쉬움
6. **기기 OCR 텍스트 힌트** — 한국어에서 효과 큼, 보통
7. **SQL 엔티티 판정 + advisory lock + 애매한 건 큐** — 보통
8. **부분 JSON 스트리밍 + 낙관적 UI** — 체감 속도, 보통
9. **확신도 대신 검증으로 보강 판단** — 스키마가 불완전하거나 상호명이 OCR 텍스트에 없으면 보강
10. 그래도 p95가 5초를 넘으면 Priority/Fast 요금제(가격 2배 안팎)

**실측이 필요합니다.** 한국어 SNS 스크린샷 → 지식 그래프 파이프라인 전체를 잰 공개 사례는 없었습니다. 스크린샷 200장 평가 세트를 만들어 직접 재야 합니다.
