## Luffi: Korean ecosystem research (as of 2026-09-29)

I ran about 52 web searches, mostly in Korean, and about 45 page fetches. The session's shared search budget ran out before I could cover the YouTube channels (조코딩, 테디노트, 안될공학), OKKY, 커리어리 and 요즘IT, so those are gaps. Anything marked **[unverified]** I could not confirm at the source.

### 1. Korean practitioners on memory, knowledge graphs and agents

- **[LabHub: "AI 에이전트의 메모리는 실제로 어떻게 만드는가"](https://www.youngju.dev/blog/2026-07-17-agent-memory-what-is-actually-measured)** (2026-07-17; redirects to labhub.hopto.org)
  - On LoCoMo, putting the full conversation in context scored 72.9% and graph memory scored 68.4%.
  - Recommended order: compaction plus file memory first, vector search only after you see retrieval failures, and graphs only for facts that change over time. "Failure should precede architecture."
  - *For Luffi:* each user's capture corpus is small. Don't start with full GraphRAG. Use the graph for intent state that changes over time (want → visited → stale).
- **[AI매터스, 김탄휴: the pitfalls of llm-wiki](https://aimatters.co.kr/news-report/42742/)** (2026-05-21)
  - An LLM hallucination becomes a "fact" that quietly spreads to every linked page. Ongoing token cost and scale are the other problems.
  - **[PyTorchKR thread](https://discuss.pytorch.kr/t/llm-wiki-karpathy/10843)** (2026-06-21) reached the practical answer: treat the wiki or graph as a *navigation map*, and fetch the original sources with BM25 plus vector search.
  - *For Luffi:* every inferred intent edge needs provenance and a confidence score. Inferred edges must never overwrite facts that came from the user's own captures.
- **[정이태 × 테디노트 GraphRAG talk, summarized on velog](https://velog.io/@looa0807/GraphRAG-%EC%9C%A0%ED%8A%9C%EB%B8%8C-%EC%98%81%EC%83%81-%EC%A0%95%EB%A6%AC)** (2025-04-04)
  - The main failure points are the same entity written in different forms, and irrelevant graph paths confusing the LLM. Suggested fix: route queries by entity type.
  - The **[Graph User Group newsletter](https://www.graphusergroup.com/2026nyeon-9weol-3juca-geuraepeu-omakase-2/)** (2026-09-13) makes a similar point: start from a real use case, not a large ontology.
  - *For Luffi:* use a small fixed schema (Place, Product, Recipe, Brand, Task, Intent) rather than open-ended extraction.
- **[우아한형제들: 리뷰의 온도](https://techblog.woowahan.com/25888/)** (2026-03-20, data science team)
  - An LLM judge labeled 100k reviews in hours, then they distilled it into an ELECTRA model for production and used Bayesian smoothing.
  - A/B testing exposed a bias: café reviews scored too high. Reorder rate ended about 54% above search-based discovery.
  - *For Luffi:* have the LLM label, then train cheap classifiers for intent and category. Audit for per-category bias.
- **[우아한형제들: harness engineering](https://techblog.woowahan.com/26177/)** (2026-04-17, 이재홍)
  - Scripts that pre-extract metadata cut context use by 96.5%.
  - LangChain's CEO says the same thing in **[Korean coverage](https://m.news.nate.com/view/20260307n05988)** (2026-03-07): harness engineering is an extension of context engineering.
- **Kakao's proactive AI**
  - "카나나 in 카카오톡" pulls dates and to-dos out of chats and suggests restaurants or gifts based on the conversation. Kakao calls AI "that doesn't disrupt daily life" its main challenge ([kidd, 2026-04-23](https://kidd.co.kr/news/245787)).
  - The standalone Kanana app shuts down on **2026-10-15** so Kakao can focus inside KakaoTalk ([한국일보, 2026-09-15](https://www.hankookilbo.com/news/article/A2026091517040005335)).
  - *For Luffi:* proactive features win where users already spend time. Set a strict limit on how often you notify.
- **당근** built its own recommendation foundation model instead of leaning on LLMs; the paper was accepted at SIGIR 2026 ([byline, 2026-04-21](https://byline.network/2026/04/17_28182764/)).

### 2. Korean-specific stack

**Embeddings**
- **[ko-embedding-leaderboard](https://github.com/OnAnd0n/ko-embedding-leaderboard)** ([announced on PyTorchKR, 2026-07-26](https://discuss.pytorch.kr/t/ko-embedding-leaderboard/11416)); NDCG averaged over 7 Korean retrieval sets:

  | Model | Score |
  |---|---|
  | pplx-embed-v1-4b | 82.79 |
  | **dragonkue/snowflake-arctic-embed-l-v2.0-ko** | 82.14 |
  | PIXIE-Rune-v1.0 | 81.57 |
  | Qwen3-Embedding-4B | 81.37 |
  | KURE-v1 | 80.76 |
  | bge-m3 | 79.30 |
  | Qwen3-Embedding-0.6B | 75.88 |

  OpenAI and Upstage are not listed.
- The **[snowflake-ko model card](https://huggingface.co/dragonkue/snowflake-arctic-embed-l-v2.0-ko)** puts OpenAI text-embedding-3-large at 0.662 NDCG@10 against 0.740 for the Korean-tuned model. That is the model author's own benchmark. The model is Apache-2.0, 1024-dimensional and 8k context, so it fits pgvector.
- **[KURE-v2](https://github.com/nlpai-lab/KURE)** (고려대 NLP&AI Lab, 2026-08-29)
  - A ColBERT-style multi-vector model built on SKT A.X-Encoder, 154M parameters, 8k context. Scores 0.816 NDCG@10 against 0.751 for bge-m3.
  - It needs PyLate and MaxSim scoring, which pgvector does not support, so it is realistic only as a second-stage scorer.
  - License is listed as MIT on GitHub but Apache-2.0 on Hugging Face.
- Small practitioner tests disagree with each other: bge-m3 beat KURE-v1 on Hit@5 (0.85 vs 0.80, 20 queries, [2026-09-27](https://github.com/YooGyeongMo/kv-cache-eval-agentic-rag/issues/2)), while KURE-v1 led on top-1 (0.914) in [another test (2026-09-28)](https://github.com/URECA-Cking/Cking-LLM-Benchmark/issues/6). Test on your own queries.
- **Upstage solar-embedding** claims to beat OpenAI on Korean, but that is the vendor's claim ([Upstage](https://ko.upstage.ai/feed/tech/solar-embedding-1-large)).
- I found **no public embedding model** from HyperCLOVA X SEED **[unverified]**. Kanana-v-embedding, Kakao's multimodal model, is internal only ([Kakao, 2025-12-12](https://www.kakaocorp.com/page/detail/11846)).

**Reranker**
- **[dragonkue/bge-reranker-v2-m3-ko](https://huggingface.co/dragonkue/bge-reranker-v2-m3-ko)** (Apache-2.0): top-1 F1 of 0.912, against 0.877 for the base model and 0.851 for Dongjin-kr/ko-reranker, on a Korean finance benchmark.

**OCR**
- **[AutoRAG team](https://velog.io/@autorag/RAG%EC%97%90%EC%84%9C-%ED%95%9C%EA%B5%AD%EC%96%B4-OCRClova-OCR-Upstage-Llama-Parse-%EC%8D%A8%EB%B3%B4%EA%B8%B0)** (2024-08): Clova OCR is best on complex tables but its JSON output is awkward. Upstage Document Parse returns HTML and is the easiest to plug in. LlamaParse is weaker on Korean.
- **[Lido](https://www.lido.app/kr/clova-ocr-daean)** (a vendor, 2026-07-22) claims Clova is 97–99% accurate on Korean at about ₩50 per call **[unverified]**.
- **PaddleOCR PP-OCRv6** (2026-06-11): the single unified model covers Chinese, English, Japanese and Latin scripts, **not Korean** ([repo](https://github.com/PaddlePaddle/PaddleOCR)). Korean needs the separate model or the VL model.
- **[EXAONE 4.5](https://www.lgresearch.ai/blog/view?seq=640)** (2026-04-09): a 33B open-weight vision-language model. It reports strong OCRBench v2 results and beats Qwen3-VL on Korean benchmarks, but it is heavy for a two-person team.

**Tokenizer and search**
- **[Kiwi](https://github.com/bab2min/Kiwi)**: about 87% accuracy on web text and 94% on formal text. It has typo correction and a user dictionary. Bindings exist for JS/WASM, **Flutter (flutter_kiwi_nlp, community-maintained)**, Java and Rust. A vendor comparison ([Bareun](https://bareun.ai/docs/compare/morph-analyzers/)) recommends mecab-ko for formal text whose words are already in the dictionary.
- **[Mimul](https://www.mimul.com/blog/paradedb-korean/)** (updated 2026-04-05) timed the long compound "디지털트랜스포메이션": ParadeDB BM25 took 2.8ms, a mecab tsvector took 96ms. The article says the tokenizer is Lindera with IPADIC; ko-dic seems more likely **[unverified]**.
- **[es-hangul](https://github.com/toss/es-hangul)** (Toss, MIT) handles initial-consonant (초성) search and jamo decomposition, which is useful for fuzzy matching of shop names in Node.

**Place and entity linking**
- **Kakao's official answers on developer forum threads** ([2026-07-14](https://devtalk.kakao.com/t/api-1/150668), [2026-09-17](https://devtalk.kakao.com/t/topic/151720), [2026-09-27](https://devtalk.kakao.com/t/local-api/151753)):
  - Local API results may **not be stored**, even the shop name on its own. Only **place_id and the place URL** may be stored.
  - Linking a Kakao place_id to data from other sources has no extra conditions.
  - There is no official way to detect when a place has closed or moved.
- **[One team's place-matching batch](https://github.com/mamoki-contest/tour_backend/issues/55)**:
  - Name normalization fails when the same place has different names (경포해변 vs 경포해수욕장).
  - They match to the nearest Kakao result within 300m, keep low-confidence matches out of the metrics, and are still short of their 90% match-rate target.
- **[소상공인 상가(상권)정보](https://www.data.go.kr/data/15083033/fileData.do)** (snapshot of 2026-03-31) is open data with shop names, addresses and coordinates that you are allowed to store.

**Recommended stack:**
- **Retrieval:** pgvector with snowflake-arctic-embed-l-v2.0-ko or bge-m3, self-hosted.
- **Keyword search:** BM25 over Kiwi-tokenized text.
- **Reranking:** bge-reranker-v2-m3-ko.
- **OCR:** on-device OCR first, then the OpenAI vision model for structured extraction, with Clova as fallback for dense text. This is my judgment; I did not verify Korean OCR on iOS or Android this session.
- **Places:** store the Kakao place_id plus your own catalog built from 상가정보.

### 4. Regulatory must-knows

- **위치정보법**
  - Sending device coordinates to the server for recommendations or geofences requires filing **위치기반서비스사업 신고**. Not storing the coordinates does not exempt you, per the Location Information Support Center as cited in [a project's legal notes (2026-08-25)](https://github.com/uuusun/RunningGu/issues/195).
  - What follows: separate location-service terms, a separate consent for personal location data, and an automatic log of who received location data and when.
  - Small businesses may operate for one month before filing. Filing is free and takes about two weeks ([캐치시큐](https://www.catchsecu.com/archives/14060)).
  - Operating without filing carries up to 3 years in prison or ₩30M. Street addresses count as personal information, not location data.
  - Whether geofencing that stays entirely on the device needs a filing is unclear. Ask the Location Information Support Center ([lbsc.kr](https://www.lbsc.kr/)).
- **개인정보보호법**
  - PIPC's guide on processing personal data for generative AI ([2025-08-06](https://www.pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS074&mCode=C020010000&nttId=11410)) says you need a legal basis, must disclose the transfer abroad to OpenAI, and must not train on user inputs without a separate basis.
  - Screenshots often contain other people's data (DM names, faces) and possibly sensitive categories.
  - The automated-decision rights in Art. 37-2 (in force since 2024-03) probably don't cover task suggestions, since they apply only to decisions with a significant effect. That's my judgment, but disclose the logic anyway.
  - An amendment takes effect 2026-09-11: fines up to 10% of revenue in aggravated cases, and notice within 72 hours of a *possible* breach ([datalaw.kr](https://datalaw.kr/guides/pipa-2026-amendment/); unofficial).
- **마이데이터:** the right to have your data transmitted now covers every sector as of **2026-08-20**. Obligations to send data fall on large holders and mostly start in 2027 ([ZDNet](https://zdnet.co.kr/view/?no=20260216123214)). Longer term, users could import their shopping data.
- **AI 기본법** (effective 2026-01-22): requires telling users when generative AI is used **[unverified this session]**.

### 5. Takeaways

1. **Don't rely on OpenAI embeddings alone for Korean.** Add Korean-tuned dense embeddings, Kiwi-tokenized BM25 and the Korean reranker, then check against about 100 of your own queries, because practitioner results disagree.
2. **Keep memory simple first.** Use compaction plus per-user fact files, and use the graph only for intent state that changes over time. Every inferred edge carries provenance, following the llm-wiki warnings.
3. **Design around Kakao's storage rule.** Store only the Kakao place_id. Build a catalog you are allowed to store from 상가정보. Score name and address separately, and send ambiguous matches to a review queue instead of auto-confirming.
4. **Don't compete on in-the-moment suggestions.** Naver, Kakao, Samsung and Apple now own that. Luffi's wedge is turning cross-app saved intent into TaskBoards with replanning. Keep a strict notification limit, since Kakao itself names disruption as the risk.
5. **Sort out compliance before shipping location reminders.** File the 위치기반서비스사업 신고, collect the separate consents, disclose the transfer abroad to OpenAI in the privacy policy, and handle third parties' data in screenshots.
