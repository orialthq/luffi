# Luffi fast lane: research findings (as of 2026-09-29)

**How this was done:** 43 web searches, then the search budget ran out. After that I read primary pages directly. Tags: **[V]** means a vendor claim, **[U]** means unverified or my own estimate. All $/capture figures assume a 1170×2532 screenshot, about 800 prompt tokens and at most 200–400 output tokens.

## Bottom line
- **Likely cause of the 20 s (not measured):** reasoning tokens plus long JSON output. OpenAI's latency guide says cutting output tokens by 50% cuts latency by about 50%, while cutting input by 50% saves only 1–5% ([OpenAI latency guide](https://developers.openai.com/api/docs/guides/latency-optimization)).
- **Reasoning also hurts Korean accuracy.** On KOCRBench, Gemini 2.5 Thinking fell from 212 to 184 ([arXiv 2510.02543](https://arxiv.org/html/2510.02543), 2025-10-02).
- **What gets you under 3 s and ~$0.001:** turn reasoning off, cap the output, and move to a Flash-Lite or Luna-class model.
- **Replace the 24 h Batch fallback with Flex.** Flex costs the same as Batch but finishes in minutes, not up to 24 h.
- **Don't build on Gemini 2.5.** The Gemini changelog says 2.5 models are limited to existing users ([changelog](https://ai.google.dev/gemini-api/docs/changelog)).

## 1. Fast-lane architecture and latency budget

**Evidence for the extraction step (step 4):**
- Roboflow Vision Evals (2026-09-28) measured Gemini 3.5 Flash-Lite at **2.7 s and $0.0014 per sample** ([Roboflow](https://playground.roboflow.com/models/google/gemini-3-5-flash-lite)).
- Gladly reports **P95 1.8 s** for a full text reply on 3.1 Flash-Lite [V] ([Google Cloud blog](https://cloud.google.com/blog/products/ai-machine-learning/gemini-3-1-flash-lite-is-now-generally-available), 2026-05-08).
- Artificial Analysis TTFT figures are misleading for this use: they are measured with 10k-token inputs and default or maximum reasoning. That is how GPT-6 Luna shows 94 s and 3.5 Flash-Lite shows 9.6 s ([AA Luna](https://artificialanalysis.ai/models/gpt-6-luna); [AA 3.5 FL](https://artificialanalysis.ai/models/gemini-3-5-flash-lite)).

**Other models checked:**
- **Excluded for commercial use:** VARCO-VISION-2.0-1.7B-OCR is CC-BY-NC.
- **Licence check needed:** Kakao kanana-1.5-v-3b (Korean OCR 85.93 [V]) and HyperCLOVAX-SEED-Vision-3B both use custom licences.

- **KLOCR** scores 94.6% Korean word accuracy against 32.6% for an older PaddleOCR ([arXiv 2510.02543](https://arxiv.org/html/2510.02543)).

**OCR first vs. image-only:** On KOCRBench, adding OCR text to the prompt raised key-information-extraction scores by **29–61 points** for every model tested, and smaller models gained the most. Recommended hybrid: send the image plus the on-device OCR text. When OCR confidence is high and the layout is simple, use a text-only call instead (~1,500 tokens, about $0.0003 on Luna).

## 3. On-device pre-processing
- **Apple Vision text recognition** has supported Korean since revision 3 / iOS 16. Auto language detection works only in "accurate" mode ([WWDC22](https://developer.apple.com/videos/play/wwdc2022/10024/)). The newer iOS 26 document request covers 26 languages but gives no word-level boxes for Korean. Flutter options: `apple_vision_recognize_text`, `flutter_native_ocr`, or a ~50-line platform channel.
- **ML Kit Text Recognition v2 (Korean)** runs on Android and iOS. The Flutter package is `google_mlkit_text_recognition` 0.17.1; you must add the Korean dependency in Gradle/Podfile ([pub.dev](https://pub.dev/packages/google_mlkit_text_recognition)). Google says real-time speed is expected for Latin script and is slower for other scripts, and each script model adds about 38 MB.
- **Apple Foundation Models (iOS 27)** now accepts images on-device. The context is 4,096 tokens; a photo used about 323 tokens in one example ([Magda](https://ivanmagda.dev/posts/wwdc26-foundation-models-year-two/), 2026-06-12). Korean is a supported language ([Apple ML](https://machinelearning.apple.com/research/introducing-third-generation-of-apple-foundation-models), 2026-06-08). Flutter: `cupertino_fundations_models` supports structured output and tools; `foundation_models_framework` is beta. **Use it for triage only** (e.g. "is this a place, product or recipe?"), not full extraction.
- **Gemini Nano Prompt API** (Android, beta): accepts image + text, input must stay under 4,000 tokens. Google itself recommends running ML Kit OCR before calling the Prompt API ([docs](https://developers.google.com/ml-kit/genai/prompt/android/get-started)). A search snippet said prompts are validated only for English and Korean, but the page I read did not confirm it [U].

## 4. Knowledge-graph updates in milliseconds
**Entity resolution on the hot path (no LLM):**
1. Normalise the name (NFKC, strip spaces and punctuation, drop branch suffixes like "…점" and "(주)"), then look up an exact unique key `(user_id, type, norm_key)` with `ON CONFLICT`.
2. If no match, compare against the user's entities of the same type using:
   - pg_trgm (needs a non-C LC_CTYPE for Hangul); pg_bigm fits 2-syllable words better but is rare on managed Postgres;
   - es-hangul `disassemble` + edit distance, and `getChoseong` for initial-consonant search ([toss/es-hangul](https://github.com/toss/es-hangul));
   - exact vector search over that user's entities.
3. Decide:
   - Merge automatically at high similarity when address or phone also match.
   - Create a new node at low similarity.
   - Anything in between gets a provisional `possible_same_as` edge and goes to a background LLM job.

Type-aware blocking beats semantic blocking for this ([arXiv 2510.14271](https://arxiv.org/html/2510.14271)).

**Concurrency:** take a `pg_advisory_xact_lock(hashtext(user_id))` at the start of each capture transaction. It serialises a user's burst uploads and releases on commit or rollback. Keep a composite `(user_id, …)` key on every table.

**Replanning:** write to an outbox table, then use LISTEN/NOTIFY or pg-boss. Debounce 1–2 s per user and replan only the tasks linked to changed entities.

## 5. Retrieval on per-user graphs
- **Vector search:** per-user data is small, so a B-tree on `user_id` plus exact distance gives 100% recall ([pgvector README](https://github.com/pgvector/pgvector), v0.8.6). Switch on `hnsw.iterative_scan` (0.8+) only when a user grows large; it raises tail latency.
- **Korean keyword search:** ParadeDB `pg_search` with the Lindera KoDic tokenizer measured **2.8 ms, vs 12.9 ms for LIKE with pg_trgm and 96 ms for tsvector with mecab-ko**, on a long compound-word query ([Mimul](https://www.mimul.com/blog/paradedb-korean/), 2026-04-05).
- **Combining the two:** reciprocal rank fusion in plain SQL ([Supabase](https://supabase.com/docs/guides/ai/hybrid-search), rrf_k=50).
- **Rerankers:** P95 on an H100 with top-100 candidates: bge-reranker-v2-m3 **215 ms**, Qwen3-Reranker-0.6B **~400 ms** ([AIMultiple](https://aimultiple.com/rerankers), 2026-02-26). Qwen3-Reranker-0.6B scores MMTEB-R 66.4 vs 58.4 for bge [V] ([model card](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B)). Keep reranking out of the capture path; use it only for TaskBoard or search queries.

## 6. Real-world numbers
- **Gemini 3.8 Flash on Roboflow:** high effort cost 27× more and was 10.3× slower for only +1.5 OCR points. Low effort was best at extraction.
- **Hybrid OCR→LLM paper:** direct LLM extraction took 13.4–13.6 s and was over 90% of pipeline time; the table-based approach was 40–50× faster ([arXiv 2510.10138](https://arxiv.org/pdf/2510.10138); summary only [U]).
- **Receipts:** GPT-5 nano 58% vs Gemini 2.5 Flash-Lite 85% on receipt extraction (Medium post, page blocked [U]).
- **Photo-memory app:** a similar app on Gemini 2.0 Flash claimed "sub-2 s" per photo (Bitcot; page blocked [U]).
- I found no practitioner post covering the whole Korean screenshot-to-knowledge-graph pipeline. Build a 200-screenshot Korean eval set and measure yourself.

## 7. Techniques ranked by impact vs. effort
1. **Reasoning off and ≤200 output tokens with short JSON keys.** Very high impact, a few hours of work.
2. **Switch to Flash-Lite / Luna and downscale images** (Gemini media_resolution, OpenAI detail). High impact, cost drops 3–10×; about a day plus an eval set.
3. **Parallelise:** process captures concurrently, and run OCR alongside upload and embedding alongside the LLM call. High impact, low effort. Watch rate limits: Luna tier 1 is 500 requests/min.
4. **Batch → Flex for background work.** OpenAI Flex is billed at Batch rates and a 429 costs nothing ([docs](https://developers.openai.com/api/docs/guides/flex-processing)); Gemini Flex targets 1–15 min ([docs](https://ai.google.dev/gemini-api/docs/priority-inference)). Low effort.
5. **SHA + dHash dedup.** Tune the Hamming threshold on your own data; about ≤5 of 64 bits is a common starting point ([dhash](https://github.com/ClaudiuCeia/dhash)). Low effort.
6. **On-device OCR text as a hint, with a text-only path when OCR is confident.** High impact on Korean key-info extraction, medium effort.
7. **Hot-path entity resolution in SQL + advisory lock + queue for ambiguous cases.** Medium effort.
8. **Stream partial JSON with an optimistic UI** (Vercel AI SDK `streamObject`). Improves perceived speed, medium effort.
9. **Validation-based escalation, not logprobs.** Escalate when the schema is incomplete or the extracted shop name is not fuzzy-found in the OCR text. Confidence scores are miscalibrated ([UCCI](https://arxiv.org/pdf/2605.18796), 2026-05).
10. **Priority / Fast tier, only if p95 is still above 5 s.** Gemini Priority is +75–100% price; OpenAI Fast mode is 2× (Luna $0.20/$1.00).
11. **Prompt caching: low value here.** Each image is unique, and the minimum cacheable prefix is 4,096 tokens on Gemini 3.5+ Flash, 1,024 on OpenAI, and 4,096 on Haiku 4.5.
12. **Regional endpoints: mainly for compliance.** OpenAI offers Korea data residency with a 10% surcharge on models released after 2026-03-05 ([OpenAI](https://openai.com/index/introducing-data-residency-in-asia/)). Whether Gemini is available in the Vertex Seoul region is [U].
